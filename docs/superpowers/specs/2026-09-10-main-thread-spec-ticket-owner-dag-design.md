## 1. 问题、目标与范围

当前 Owner Workflow 已有 Registry、单 Owner 执行、固定验证、隔离工作区与 DAG 恢复，但规划、审批和修复状态耦合较强。用户希望将需求与工作拆解先在主线程确定，再编排运行图，让小模型承担准确的执行任务；Owner 保留长期模块责任，公共模块变更由其 Owner 独立判断影响。

目标工作流为：

```text
需求讨论与总结（主线程）
  → 明确进入 Spec（主线程）
  → 形成 Ticket（主线程）
  → 编排 Owner 执行 DAG
  → Runner 根据依赖、空闲执行槽位和 Owner/资源占用推进
  → 执行问题反馈主线程，继续 / 局部改图 / 修订工作和技术合同
  → 自动验证、审查和技术修复
  → 在已授权范围内完成交付，或带证据报告无法推进
```

产品行为、需求取舍、范围变化和真实外部权限缺失时，由主线程向用户提出。技术恢复不设置固定的人工轮次门禁。

### 非目标

- 除 U10 明确授权的文档权限外，不将写文档授权扩展成完整流程实现授权。
- 不照搬 Ghost Matt 的逐轮等待用户确认、Codex 工具名、固定模型名或 PR 流程。
- 不把所有 Owner 会诊作为进入 Spec 前的独立必经阶段。
- 不取消 Owner 隔离或用最终提交审计冒充共享目录中的逐次写入保护。
- 不自动发布、推送、授予新权限或迁移正在运行的旧现场。
- 不追求一次预测所有实现细节，也不保证每项工程问题必然能自主解决。
- 不在首版引入多机调度或为每个思考步骤构建递归 Composite 图。

## 2. 已确认决定与默认工程原则

### 已确认方向

- Spec 和 Ticket 的统一产出责任在主线程，先于执行 DAG。
- Owner 保存修改原因、版本与现状，并对公共模块变更独立判断。
- 小模型执行明确任务；Runner 根据资源和 Owner 推进工作。
- 问题先反馈主代理，由其决定继续、改图或修订需求/工作。
- 除需求讨论、必要的需求决定及真实权限事项外，不要求用户过程性参与。
- 取消“每轮结束等待用户确认”的早期方案。

### 本规格采用的工程原则

以下用于表达可验证合同，不冒充用户指定的实现细节：保留 Runtime 为执行状态唯一写入者；保留现有 scope/lease/固定验证保证；绑定产物版本并局部失效传播；用实际证据识别进展；预算耗尽时保存现场并形成失败报告。具体接口、持久化格式、模型配置和预算数值已由后续有界实现及第12节回填固定。

## 4. 模块职责与权威归属

| 责任方 | 输入 | 输出与权威 | 边界 |
| --- | --- | --- | --- |
| 用户 / 主线程交互 | 需求讨论、执行中暴露的业务取舍 | 用户决定；主线程记录来源与授权范围 | 普通讨论不自动成为实施意图 |
| 主线程规划协调 | 用户意图、当前代码、Owner 历史、执行反馈 | Spec、Ticket、技术决定及计划修订建议 | 不能静默改变产品承诺或降低 AC |
| Owner 判断 | 本模块合同、版本、请求、消费者事实、执行偏差 | 有理由与证据的决定、替代方案、执行约束 | 下游请求不等于批准；记忆不授予 scope |
| 小模型执行 | 单 Owner 执行包、固定基线及允许能力 | 修改、定向结果、偏差报告 | 不自行扩大写入权、改公共合同、操纵 Git 集成或工作流状态 |
| Runtime | 已授权的版本化产物、执行与宿主观测 | 校验、状态持久化、lease、固定验证、提交/集成、版本切换 | 唯一执行状态权威；模型结论须按绑定核验 |
| Runner | Runtime 给出的就绪动作及当前容量 | 执行/等待/观测回执 | 不独立解释业务需求或自行重写图 |
| Owner 历史整理 | 固定结果、决定及其来源 | 原始历史、当前合同投影、可检索解释摘要 | 摘要不能反向覆盖原始事实或提升权限 |

Owner 是长期身份，不要求长期存活会话。判断与执行可使用不同短期会话，但都由 Runtime 创建和绑定；不要求突破当前 Owner 禁止派生后代代理的规则。

主线程可以读取 Owner 历史与证据来完成 Spec/Ticket；不建立未经用户确认的“先由另一套 Planner/Owner 主持 Spec”的流程。必要的公共 Owner 评估可成为有明确输入、输出和依赖的执行准备节点；消费者实现等待其有效合同，不能先猜接口再会诊。

## 5. 产物与跨模块合同

### 5.1 Spec → Ticket → 执行计划

Spec 包含目标、范围、稳定 AC、模块合同、兼容约束及未决事项。Ticket 引用 Spec 修订和 AC，描述工作、完成要求及逻辑依赖。一个 Ticket 可以映射多个单 Owner 执行包，并保留一个完整行为验收点。

执行包记录 Ticket/AC/合同来源、Owner、基线内容、允许范围、目标行为、前置产物、固定验证和偏差条件。新增文件可以属于受控文件族；不要在规格阶段锁死所有未来路径。

Runtime 编排时必须验证：引用存在且版本匹配、Owner 正式登记、write 在 scope 内、执行依赖无环、固定验证合法、现有入口/cwd 可用。未来才会创建的验证入口必须有明确生产者和解锁检查。含未决合同的消费者节点不可执行；无关就绪范围可继续。

本次授权若为“只生成 Spec”，流程停在 Spec 交付；若已明确授权完成开发，则阶段切换不重复索要 Spec/Ticket/DAG 的人工同意。进入 Spec 不应被技术实现无条件解释为对所有后续行动的授权。

### 5.2 下游 → 公共 Owner

变更请求包含稳定请求身份、请求方、目标 Owner、需要的行为、现状不足证据、合同/代码版本和建议。公共 Owner 必须给出有依据的结果：现有能力已足够、接受兼容扩展、需要迁移、拒绝并提供原因/替代方案，或缺少具体事实。

公共 Owner 根据真实调用方判断影响，必要时由消费者 Owner 核对。公共依赖不等于 Registry 父子关系；模块调用环不直接变成执行依赖环。兼容扩展、消费者迁移和旧形式移除可形成有序执行；不能分阶段有效时，明确共同集成候选的验收范围。

决定与对应合同版本绑定。Owner 拒绝方案后，主线程根据既有需求协调替代方案；只有改变业务取舍才请求用户，不将每次技术分歧都转成用户审批。

### 5.3 Runtime → Runner → 执行者

只有前置结果有效、合同/计划版本有效、Owner 空闲、资源无冲突且有可用执行槽位的节点才能被派发。任务数量超过容量时保留就绪队列，不占用虚假的 running 状态。

同一 Owner 默认同时一个执行者；共享文件由正式 Owner 唯一负责。测试端口、数据库和构建输出互斥独立于数据依赖。隔离 worktree 保留，不能因为分支不同就允许两个责任方提交同一公共路径。

执行回执需绑定 workflow、执行节点、Owner、当前执行尝试及适用版本。过期或重复回执不得覆盖当前状态或造成重复提交。具体字段与API由后续版本化实现合同固定，逻辑身份不得省略。

### 5.4 执行者 → 主线程的偏差反馈

反馈含预期、实际、证据、相关版本、受影响工作和需要裁决的问题。主线程选择最小必要动作：

| 类型 | 动作 |
| --- | --- |
| 实现偏离已确定合同 | 原节点有限修复，通常不改 Spec/Ticket/DAG |
| 环境或固定入口缺失 | 获取实际错误，确定修复责任；必要时补前置工作 |
| Owner 分配、写入范围、执行依赖有误 | 修订受影响执行图，重新绑定权限，不让执行者自行扩权 |
| 工作遗漏但业务需求不变 | 修订 Ticket 并同步执行图 |
| 技术合同不成立但目标仍不变 | 对应 Owner 判断，主线程修订技术合同及受影响工作 |
| 产品行为、范围或承诺需要改变 | 主线程将证据与选项交给用户，决定前不实施受影响变化 |

Runner 不根据错误文字自行选择业务修改。“用户取消连接时如何释放资源”不因包含“用户”就被标为外部授权。无法自主解决的技术失败应形成可解释报告，不能伪装成需求决定。

### 5.5 版本切换与失效传播

Spec、Ticket 和执行图有各自可追溯修订与引用；状态投影由 Runtime 生成，不允许可写 Markdown 进度与 Runtime JSON 各自成为调度真源。当前候选形成期间到达的新意图不能悄悄改变候选内容。

受影响的运行节点在安全边界暂停或停止，旧权限和结果绑定失效；先保留工作区及证据，再切换有效版本。无关节点与已证明仍有效的成果继续保留。消费者使用的合同或产物变化时，相关结果进入待检查，不能混用旧结果宣称通过。

### 5.6 验收、交付与历史

Owner 核对修改理由、合同、兼容性和实际 diff；Runtime 核验候选范围与固定验证。审查和测试绑定实际内容，不能只用 HEAD 忽略未提交源码，也不能在候选变化后复用失效证据。

停止相关写入后，对集成候选运行 AC 和受影响回归。独立项失败继续收集其他可执行项，区分断言失败、编译/收集失败、超时、跳过、未运行、阻塞和通过；零用例不算通过。技术缺陷在授权范围内继续处理，不设置每轮等待用户确认。

原始修改原因、版本、决定及验证在完成/集成边界可靠记账。当前模块合同是可核验投影，历史决定不自动继续有效；解释摘要可随后整理，失败时不撤销已核验代码结果。后续Owner通过sealed worklog、Git来源提交及digest恢复依据；Runtime只重试摘要，不能从缺失来源猜测或补造历史。

所有范围内 AC 满足必要证据后才可交付。失败候选保留现场，不能通过降低 AC 或把未运行标绿完成工作。提交、推送与外部操作仍受已有授权及项目 Git 同步规则约束。

### 5.7 文档就绪与执行输入固定

下表是跨模块需要保持的逻辑记录，不是已存在的 API 或最终序列化格式。接口命名和持久化实现可调整，但不能省略版本、来源或归属校验。

| 记录 | 必须表达的事实 | 唯一写入方 / 消费者 |
| --- | --- | --- |
| 规划文档集合 | 稳定 Spec ID/修订、所选 Ticket ID/修订、各自路径和内容摘要、AC/合同引用、就绪及阻塞范围 | 主线程整理内容；Runtime 校验并冻结；编排器读取 |
| 规划快照 | 项目身份、源文件内容与摘要、代码基线、授权来源及范围、所选工作、父快照、创建原因 | Runtime 持久化为不可变输入；Owner/Reviewer/执行者按引用读取 |
| 执行版本 | 规划快照引用、Registry digest、DAG digest、父执行版本、任务到 Ticket/AC/合同的映射 | Runtime 激活；Runner 仅消费当前有效版本 |
| 执行回执 | 项目/Workflow/执行版本、节点、Owner、attempt、租约代次、实际代码/验证证据摘要 | Runtime 核验、去重、结算；主线程读取结果 |

文档写入和工作就绪是两件事。主线程可以持续修改草稿；进入编排前，只冻结本次已就绪且已获实施授权的范围。Runtime 验证文件存在、位于允许范围、内容未变、稳定编号及引用一致；语义上的需求覆盖和合同正确性仍由主线程与独立审查承担。空 Ticket 集合或没有可执行范围时返回明确的“无可执行工作/具体阻塞”，不创建空 Workflow 反复规划。

执行者必须读取被固定的内容，不能通过同一路径读取后来改写的文档并把它视为原快照。Markdown 的 `progress.md` 可以记讨论与待办，但节点完成、正式验证和执行版本由 Runtime 生成投影；主线程把状态文字改成“通过”不会解锁后继节点。

以下“基线接缝/拟议处理”保留R4制定时的问题与选型依据；当前生产实现及最终状态以第9、10节的后续回填为准。

**R4制定时的基线接缝**：`preflightWorkflow` 在默认 `requireCleanBase=true` 时检查所有非运行时改动，`startWorkflow` 再核对 `baseDigest`。本轮临时 Git 验证确认：干净仓库可开始，新增 `docs/specs/<主题>/spec.md` 后不可开始。仅放开文档写入不会自动打通这个入口。

**拟议处理原则**：保持干净代码基线要求，由 Runtime 提供有界的规划文档固定动作。已有实施授权覆盖本地文档提交时，可在当前本地分支形成仅包含本次规划文档的 checkpoint，然后重新预检并生成快照；主线程不获得 Shell 或任意 Git 提交权限。该动作必须满足：

1. 显式文档清单、预期分支/HEAD、文件修改前后摘要以及本次写入来源均已绑定；“目录在白名单内”本身不证明所有改动都属于本次任务。
2. 清单外的工作区内容和已有暂存内容保持原样，不能用全仓 `add`、stash、reset 或自动忽略文档来取得干净基线。用户与主线程同时改同一文件、来源不明或基线变化时，不自动提交合并内容。
3. 本地提交、实际 index 状态、工作区和快照形成必须具有可恢复的事务记录。中途崩溃可识别已完成的精确提交，不重复提交，也不假称工作区已同步；持久化失败时不派发节点。
4. 没有本地提交授权时仍可交付 Spec/Ticket，但不假装已具备执行条件。存在不属于本次规划的未提交代码时，保持现有阻塞及文件清单，不把它纳入规划文档 checkpoint。

以上是待验证方案，**不把独立 index、提交事务或执行快照的原子性当成现有能力**。V-02 必须先验证正常路径、同时编辑、已有暂存和崩溃恢复；在此之前，不将完整文档→DAG 集成标为可直接实施。未来若采用只读快照替代 Git checkpoint，也必须证明代码基线、文档交付和最终本地合并的一致性，不能仅绕过预检。

### 5.8 公共 Owner 的有界决定与改图

公共变更评估是有界准备工作，由 Runtime 在注册 Owner 身份下创建只读判断会话；该会话不能直接修改公共模块或 Registry。判断可以复用当前 `consultPlanningOwners` 的只读子代理与历史加载接缝，但当前 `DSH_OWNER_PLANNING_ADVICE_V1` 只是建议，不构成下面的完整决定协议。

| 输入 / 结果 | 最小合同与后续行为 |
| --- | --- |
| 变更请求 | 稳定 request ID、来源 Ticket/AC、目标 Owner、基线/合同版本、预期行为、实际不足及证据引用；重复投递同一版本请求不重复产生决定 |
| 现有能力足够 | 引用可使用的能力和验证依据；主线程修改消费者执行包，无需创建公共修改节点 |
| 接受兼容扩展 | 给出合同变化、消费者清单、兼容说明与必要验证；公共实现通过后解锁依赖该结果的消费者 |
| 需要迁移 | 给出受影响消费者和扩展/迁移/移除顺序；阶段间行为必须明确，旧形式移除以消费者迁移证据为前置 |
| 拒绝当前方案 | 说明违反的合同和证据，给出可行替代或明确不可行原因；主线程在原需求内协调，不原样重发同一方案 |
| 缺少事实 | 列出具体未知、调查责任和解除条件；一次有界调查返回事实或失败，不以“需要更多上下文”无限续期 |
| 需要业务决定 | 明确哪项原 AC/范围承诺必须改变及可选后果；主线程取得用户决定，受影响消费者保持阻塞 |

Owner 判断只覆盖其模块合同。若候选会改变其他 Owner 的既有承诺，必须取得对应 Owner 的影响结论；消费者清单不完整时返回明确未知，不把“没找到调用方”当成无人受影响。互相矛盾的决定返回主线程协调，仍消耗同一问题的恢复预算。

请求、决定、实现和验收分别有版本。判断期间源合同变化，原决定标记过期；重新评估影响范围后才生成下一候选。决定本身不直接授予写入权：兼容扩展或迁移决定由Runtime转换为绑定原request/decision digest的内部Intent，经Planner、独立Review和激活事务形成完整候选；拒绝、事实缺失或业务承诺变化仍回到主线程。Runner只执行已经激活的单Owner任务。

对于 S、A、B 的共同场景，先完成 S 的只读决定，再由 S 实现兼容合同 K2，验证 B 的恢复行为保留，最后解锁依赖 K2 的 A；无关节点不因评估占用全部执行槽位。若无法形成可验证的阶段顺序，明确使用共同集成候选或报告不可行，不将模块依赖环直接塞进 DAG。

R93/T-06已冻结协议层：[公共Owner变更协议V1](../../specs/main-thread-owner-workflow/contracts/public-owner-change-v1.md)以`contextDigest`绑定Workflow/Plan、目标Owner与合同、Ticket/AC、证据及消费者事实；请求版本连续引用前版digest，一个请求版本最多一个决定。消费者清单另有完整性位，未知清单不能解释为无人受影响。旧执行、合同或消费者上下文只产生stale投影；只有完整依据的“现有能力足够”直接给出重绑定就绪，其他五类结果保持等待实现、迁移、协调、调查或用户业务决定。该纯协议不创建会话或修改DAG；T08消费它验证真实只读Owner判断会话，B02负责生产接线。

### 5.9 候选激活、并发反馈和旧结果

候选由主线程协调形成，编排器只能细化已固定的合同和依赖，不能另写一份需求。Runtime 在 Workflow 锁内核对预期父版本、快照、Registry、独立审查结果及原授权范围，成功时一次激活完整执行版本。迟到反馈进入下一个候选；失配返回具体过期引用，保留原候选与当前有效版本，不静默套到新 HEAD。

技术修订在已有实施授权和原业务范围内，可由主线程确认后经 Runtime 激活；只有改变业务承诺或真正缺少外部权限时才等待用户。当前原生 plan/revision 批准工具仍有逐项人工门禁，不能在实施时只改提示让模型冒充用户同意；新路径必须记录自己的授权依据，并保留旧 Workflow 的原审批协议。

复用现有 `carry_valid / pending_check / abort` 分类，但补入合同/快照依赖：

- 无关节点保留；运行中的兼容变化可让旧 attempt 在原权限内完成，结果按新引用进入待检查。旧 attempt 不获得新增写入权；需要扩大权限的后续工作使用新执行包。
- Owner 变更、删除、scope 收窄或 Registry 失效须停止或隔离旧执行者，再释放写入租约；旧回执只能记入历史。
- 已完成节点的历史定义不改写；合同变化需要新的修复/验证工作，不能通过修改标题或 `done` 把历史变成另一项工作。
- 无论选择暂停还是排空，受影响的后继都必须有明确解除条件；文档候选、已激活图和实际集成版本不能各自漂移。

现有 `PlanRevision` 只固定计划快照；`approvePendingPlanRevision` 有锁、父版本、digest、Review 和任务迁移检查。这证明可复用的接缝存在，不证明 Spec/Ticket/Git 与执行版本已经原子绑定。

### 5.10 收敛：问题身份、证据、预算与停止

将模型产生的解释与 Runtime 核验的事实分开。证据义务是一个需要满足的具体要求，绑定稳定 ID、来源、目标合同/AC、当前状态和解除条件；标题只用于显示。ID 在重措辞、重启、改图和拆节点时保持继承关系。不同要求即使 category/task 相同也不能互相合并关闭。

| 情况 | 必须发生的状态变化 |
| --- | --- |
| 文案、时间戳、会话 ID、候选摘要改变 | 不增加事实证据、不关闭义务、不恢复预算 |
| 新文件内容、真实验证结果或有效决定到达 | Runtime 核验来源、版本、与义务的关联后记账；重复结果幂等，不因不相关 HEAD 变化恢复整条工作流预算 |
| Reviewer 不再列出旧问题 | 原义务仍 open，直到明确提交满足其解除条件的证据或有来源的替代决定 |
| Reviewer 声称 passed 但还有 open 义务 | 不激活或结算；返回尚未关闭的义务及其缺失证据 |
| 技术问题含“用户”“token”等词 | 关键词最多作为提示；必须有结构化的业务承诺差异或真实权限缺口，才建立用户待决事项 |
| 连续无进展 | 在固定策略集合内切换且计数；重启、重建候选和拆分任务继承同一事件预算 |
| 预算耗尽 | 停止该问题的自动尝试、保存现场、释放可安全释放资源、报告证据与失败原因；其他独立工作可继续 |

预算由 Runtime 在开始尝试前持久扣减；至少有正的有限尝试上限和每次执行超时。预算绑定问题及其派生修复，同时保留 Workflow 总上限；真实新证据可以改变下一动作，但不能无限重置总上限。模型不能自行扩额。最终数值与既有配置的兼容已由V-03及第12.6节固定；工程常数不要求用户拍定。

失败报告包括固定输入版本、未满足要求、尝试过的策略、实际证据和保留现场位置。技术失败不会被改名为“等待用户决定”以逃避结算；用户之后明确给出新范围或新预算时，Runtime 才记录新的恢复依据，旧失败历史保留。

## 6. 资源生命周期与恢复

Runtime 负责短期会话、执行尝试、Owner/资源租约与隔离现场的创建和绑定。Runner 负责驱动及回传观测；主线程关闭技术决定后由 Runtime 应用，不能让模型直接写状态文件。

完成、失败、取消和失效均需结算该次尝试，并释放其可安全释放的执行槽位与租约。释放写入权前确认旧执行者已停止或被有效隔离，不能因心跳延迟导致两个写入者并存。失败和取消默认保留修改及原始证据；未有明确清理授权不得删除用户文件或历史现场。

重启后以持久状态核对当前版本、存活执行者和有效结果；不重复运行已经完成的提交事务。挂起工作必须显示等待什么、由谁处理、怎样解除；没有负责者/解除条件的“持续运行”不是合法恢复结果。

保留有限自主恢复能力：固定范围内的执行与恢复有预算；同义表述、代理重启、节点数量变化和旧事实反复出现不能重置预算。义务关闭需要对应决定/证据，报告遗漏保持 open。预算耗尽进入明确的失败结算并交付事实，不能后台无限续跑。具体预算值使用第12.6节已验证并版本化的12/8策略、批准任务hard deadline和30秒终态观察窗口。

## 7. 代表场景与共同事实

固定一个公共会话 Owner S、连接界面 Owner A、恢复消费者 Owner B。已有合同 K1 允许 B 使用缓存恢复；目标 AC 要求 A 取消当前连接后可重连，同时保持 B 的既有恢复行为。使用版本化的本地假实现/夹具完成第一条集成验证，不要求真实钱包、生产 origin 或外部凭据。

A 提议“取消时清空所有缓存”。S 必须识别对 B 的影响，形成满足原目标的兼容方案，或者说明需要改变业务承诺。若形成 K2，只授权 S 改公共路径；A/B 执行包引用同一有效合同。若必须改变 B 的承诺，主线程等待用户决定，并允许独立工作继续。

同一夹具提供固定基线、合同、请求、Owner 归属、可追踪执行动作和原始验证结果。超时、错误入口、旧版本回执等通过边界注入，所有断言观察外部调度、实际结果和记录，不以单纯“函数返回合法枚举”替代行为验证。

### 12.1 可实施的账本不变量

新增独立的版本化恢复预算协议。Workflow记录有冻结的正整数恢复总上限及已用数；每个稳定根问题有正整数上限、已用数、关联来源、状态；每次恢复领取有Runtime提供的幂等请求ID、attempt ID、问题/task/Owner/执行版本绑定和状态。非法、缺失、零/负/非整数上限拒绝，纯状态计算不依赖墙钟、文件或模型。

一次新恢复领取同时消耗问题与Workflow各一份额度；任一级无余额则拒绝且不修改账本。相同请求、相同绑定重放返回同一attempt，不重扣；相同请求ID但不同绑定拒绝。已领取后不因失败、取消、崩溃、新证据或结果重放自动退款。正常初次业务执行不计为恢复，但仍受单次硬截止约束；计划修复若真正启动外部恢复工作也需额度，纯读取/分类/派发重放不扣费。

问题解决后保留历史及Workflow累计消耗；关闭只接纳由Runtime核验的相关来源/关闭证据，不允许模型凭文本生成新根问题或清零。纯协议层接收明确来源引用，不能宣称它已验证外部事实。任务改名、Owner/attempt/版本变化不新建原未解决问题；派生节点共享rootProblemId。根问题识别/复用及闭合生产者的实际绑定由12.2验证后固定，未就绪不能接线。

### 12.2 持久领取和执行接线的验证门槛

领取必须在实际生效的Workflow并发控制内读取最新状态、核验绑定、幂等检查并同时扣减两级余额，持久化reserved后才能启动外部工作。未能证明落盘不得启动；重启复用已reserved且未启动的attempt；启动结果不确定先对账会话/租约，不能盲目再次派发或退款。验证应区分进程中断、并发进程和断电持久性，不用内存Runtime重建冒充它们。

现有writeJsonAtomic使用临时文件加rename，saveState另有写锁，不能据此认定完整读改写与外部启动已原子化。T-14需验证持久化、并发和请求/attempt/会话身份接缝并回填具体接口；如果不成立，记录缺口并细化实现前置，T-15保持阻塞。不得在验证工单里修改生产补齐。
