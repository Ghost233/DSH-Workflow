# 主线程形成 Spec 和 Ticket，再编排 Owner 自主执行

用户希望将思考前置、保留 Owner 的长期模块责任，并在需求讨论及执行中必要的需求决定之外尽量不参与。决定由主线程先形成 Spec 与 Ticket，再将就绪工作编排为单 Owner 执行节点；Runner 根据依赖、执行槽位、Owner 和资源占用推进工作，技术偏差反馈主线程自主处理，需求取舍与真实外部授权才返回用户。

Owner 独立判断公共模块变更的理由与消费者影响，并保留原因、版本和现状记录；业务 Ticket 可以跨 Owner，具体执行包只能绑定一个 Owner。这样保留业务切片的完整性和模块责任，同时避免让一个 Planner 一次性猜出需求、Owner 合同与完整执行图。

## 取舍与影响

- 不采用“每一轮开发、测试、反思后都等待用户确认”。这是早期讨论中的建议，已被用户“除聊需求及需要我决策外，不再参与”的明确要求替代。测试和反思仍存在，技术修复默认自主推进。
- 不将所有 Owner 会诊设为进入 Spec 前的独立必经流程。Spec/Ticket 的统一产出责任在主线程；必要的 Owner 判断在执行编排和反馈中有明确位置与完成条件。
- 不用更多自动重规划替代证据。自主流程必须能识别真实进展、局部修订与不可推进的失败；停止并报告失败不等于要求用户承担工程排查。
- 自主推进受到本次授权范围约束。“只写 Spec”不授权 Ticket 拆解或开发，自动开发不自动授予推送、发布及其他外部操作权限。

本 ADR 接受的是讨论确定的架构方向，不表示当前代码已经实现。详细来源和被替代观点见[讨论记录](../analysis/2026-09-10-dsh-matt/discussion-record.md)，拟议合同和验收见[规格草稿](../superpowers/specs/2026-09-10-main-thread-spec-ticket-owner-dag-design.md)。
