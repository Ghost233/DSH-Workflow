# Browser Harness 内部插件设计访谈

## 用户目标

用户希望在 DSH Workflow 内维护一个 Browser Harness 插件，便于版本管理。当前明确提出两项能力：追踪 Skill 是否更新，以及检查和追踪本机是否安装 Browser Harness。此前讨论的使用方向是由 DSH 原生 Agent 通过 CLI 和官方 Skill 操作浏览器，并自行验收。

本记录按 `grill-with-docs` 保存设计树与访谈结果。用户随后调用 spec-delivery 进入交付，当前实施范围以[规格](../../specs/browser-harness-plugin/spec.md)为准。

## 已核对的事实

- 项目已通过 `dsh-skill-filesystem` 加载根目录 `skills/`。参见[启动装配](../../../scripts/dsh-launch-composition.mjs)。
- 应用的项目资源封装已包含根目录 `skills/`，并记录成员摘要。参见[项目资源封装](../../../macos-launcher/project-resources.mjs)。
- 现有应用版本检查只读取本地插件文件，不查询上游最新版本；实际安装值和固定值分开记录。参见[版本检查](../../../macos-launcher/runtime/plugin-versions.mjs)。
- DSH 运行中的交付清单按当前 Host 的插件解析结果展示实际版本与来源；该机制没有覆盖 Browser Harness 的 Python 包或 CLI。参见[运行交付清单](../../../agent-observation-plugin/src/delivery-inventory.mjs)。
- 服务首次启动时会读取用户的交互登录 Shell 环境，并把应用运行时目录加入 Host 的 PATH。模型 Bash 还经过工具环境、凭据清理和沙箱处理，因此管理进程、DSH Host 和模型 Bash 的命令可见性需要分别核对。参见[服务启动环境](../../../macos-launcher/runtime/service-manager.mjs)、[Bash 提供方](../../../deepseek-harness/packages/shell/bash-local/src/index.ts)和[Shell 沙箱](../../../deepseek-harness/packages/shell/bash-sandbox/src/index.ts)。
- DSH 子进程服务已有 `resolveExecutable`，可以按执行环境解析可执行路径。该操作本身不运行软件，也不查询版本；当前项目未发现通用的 CLI 安装和版本盘点入口。参见[子进程服务](../../../deepseek-harness/packages/subprocess/subprocess/src/index.ts)。
- 官方 Browser Harness 提供 CLI、Skill 和独立 MCP 入口。前期源码对比见[调研报告](../2026-10-23-browser-use-stack-comparison.md)。
- 在已核对的上游提交 `c6a941287424f32e2d20c7b7b892c8493f46808d` 中，`browser-harness skill` 读取包内 `SKILL.md`；仓库的包内技能和 skills 目录入口均链接到根技能文件。上游包声明只包含主技能和视频模板，没有声明随包提供全部 `interaction-skills/`。主技能仍引用 GitHub 默认分支的参考文档，需单独确定这些参考文件的交付范围。参见[技能读取入口](https://github.com/browser-use/browser-harness/blob/c6a941287424f32e2d20c7b7b892c8493f46808d/src/browser_harness/run.py#L111)、[包声明](https://github.com/browser-use/browser-harness/blob/c6a941287424f32e2d20c7b7b892c8493f46808d/pyproject.toml)。
- `browser-harness --version` 在连接浏览器前返回本地版本，但命令入口默认会记录遥测。本机只读检查若运行该命令，应对该子进程设置 `BH_TELEMETRY=0`，不能把默认命令行为描述为完全离线。参见[版本命令](https://github.com/browser-use/browser-harness/blob/c6a941287424f32e2d20c7b7b892c8493f46808d/src/browser_harness/run.py#L304)、[遥测开关](https://github.com/browser-use/browser-harness/blob/c6a941287424f32e2d20c7b7b892c8493f46808d/src/browser_harness/telemetry.py#L82)。

## 已确认的边界

- 首版只检查和提示，安装与升级由用户在外部完成。
- 本机安装状态以 DSH 实际执行任务时能否调用为准，显示实际路径与版本。不扫描所有 Python 环境来推断可用性。
- 官方上游通过 Git submodule 固定提交。只有用户手动要求采用更新时，才推进该基准。
- 安装后的插件不联网检查上游，不实时更新或轮询技能，不添加运行端的检查更新按钮。
- 按 Q4，普通打包检查上游技能变化，只报告差异并消费仓库固定的子模块内容，不自动采用最新 Skill。Q7、Q8 的手动更新说明不取消这项已确认的检查行为。
- 信息展示放在启动器现有版本管理列表，不新增独立 DSH 管理页。
- 用户不需要插件内单独的检查或更新按钮。拟复用启动器现有版本列表读取流程，取得一次本机安装信息，不增加后台轮询。

主 Skill 与所需配套文档从同一子模块提交交付，是当前工程建议，原文保持不改。完整方案仍待共同理解确认。已确认的交付边界见 [ADR-0011](../../adr/0011-browser-harness-build-time-skill-check.md)，领域语言见[术语表](../../../GLOSSARY.md)。

## 设计树

1. 内部插件的管理职责。
   - Q1 已确定：首版只检查和提示，安装与升级在外部完成。
   - 缺失或不可调用只报告状态；首版不据此自动安装、升级或测试浏览器任务。
2. 本机安装状态的含义。
   - Q2 已确定：以 DSH 实际可调用为准，并展示路径与版本。
   - Q5 用户修正：不增加插件内单独检查按钮。拟随启动器现有版本列表读取一次，不轮询、不连接 Chrome。
3. 更新检查。
   - Q3 曾明确要求在构建打包时检查，Q7、Q8 随后确定子模块固定、手动采用更新。
   - Q4 已明确：打包检查和报告上游差异，但仍使用固定版本。
   - Q7 已确定：使用 submodule 固定上游完整提交。
   - Q8 用户明确不自动采用更新；将其推断成取消打包时的上游查询与 Q4 不符，现已撤回该推断。Q8 原本询问的检查失败策略仍未得到直接回答。
4. 随应用交付的技能。
   - Q6 已确定：信息放在启动器现有版本管理列表。
   - 主 Skill 和配套资料从同一固定上游提交选取，上游原文不改；项目加载与打包适配由自研集成层负责。
   - 本机 CLI 版本与随包技能基准分别展示，不凭版本不同自动断言不兼容。
   - 待用户确认完整交付与验收方案。

## 第一轮问题

Q1：首版是否限定为内置官方 Skill、追踪 Skill 更新、检查本机 Browser Harness 的安装与版本，安装和升级先由用户在外部完成？推荐先做检查和提示，不在启动时自动更改环境。

Q2：是否以 DSH 实际执行任务时能调用的 Browser Harness 为安装判定，并显示路径与版本？推荐把其他环境装过但当前调用不到的情况标为当前不可用。

Q3：是否在启动时只检查本地状态，上游 Skill 更新通过页面中的检查更新操作手动查询？推荐本地检查与联网检查分开，检查失败时保留上次结果并显示时间。

用户接受 Q1、Q2 的推荐答案。用户最初接受 Q3，随后明确修正为构建打包时检查上游，安装后不做实时更新或实时检查。以后续说明为准。

## 第二轮问题

Q4：打包发现上游 Skill 变化时，是否只输出差异和提示，继续消费仓库已固定版本，采用更新时再修改仓库基准？推荐发现与采用分开，不在打包时静默改变技能内容。另一选项是打包时自动采用上游最新 Skill。

Q5：安装后的本机状态是否仅在用户点击检查本机时探测，不持续轮询、不检查上游，也不打开 Chrome？推荐手动本机检查。另一选项是启动时检查并支持手动刷新。

Q6：管理入口是否放在 DSH 内独立页面，桌面端和 Web 共用，展示随包技能版本和本机检查结果？推荐在 DSH 内提供入口。另一选项是放在启动器的版本管理列表。

用户接受 Q4 的推荐答案。对 Q5，用户明确不需要插件内部的检查更新按钮，并说明安装状态只需反映已安装事实。对 Q6，用户选择启动器的版本管理列表；此前提出的独立 DSH 管理页不采用。

## 第三轮问题

Q7：是否将官方 Skill 引用的配套参考文档一起按同一上游基准随 App 交付，并在打包时比较这组技能资料是否变化？推荐一并固定，避免内置主技能依赖浮动的在线参考文档。第三方原文保留不改，项目加载方式由自研集成层处理。

Q8：打包时若因离线、限流等原因无法检查上游，是否明确记录未完成检查，但允许继续打包仓库固定技能？推荐继续打包固定版本，不把检查失败写成没有更新。另一选项是上游检查成功后才允许打包。

用户对 Q7 指定通过 submodule 固定上游 hash。对 Q8，用户说明“不需要自动，我手动要求才更新，看 Q7”。这明确了采用新基准必须由用户发起，不取消 Q4 已接受的差异检查。此前记录取消联网查询的推断已撤回。用户尚未直接回答检查失败时是否允许继续打包固定版本。

## 完整方案草案

1. 在主仓库维护内部 Browser Harness 插件，统一记录上游技能基准、内置交付信息及本机安装状态。
2. 通过 `vendor/browser-harness` 子模块固定官方上游提交。首次基准采用此前已调研提交是工程建议；后续只有用户明确提出采用更新时才推进。
3. 主 Skill 与配套参考文档从同一固定提交随 App 交付。官方文件保持原样，项目加载方式在自研集成层处理。
4. 打包校验子模块实际提交及所选资料，记录完整提交与内容摘要。固定内容缺失或偏离基准时报告失败，不自动改变基准。另行检查上游并只报告技能差异；查询失败如何处理尚待明确。
5. 启动器现有版本管理列表展示插件版本、随包技能基准、本机 Browser Harness 版本、实际路径与安装状态。复用现有列表读取流程，不新增按钮、定时检查或 DSH 管理页。
6. 本机状态按 DSH 目标执行环境判断。无法取得该环境时明确标记未验证，不把启动器或其他虚拟环境中找到的软件冒充 DSH 可用安装。
7. 本机查询不连接或启动 Chrome，不访问上游。若调用版本命令，为该子进程关闭遥测。未安装、不可调用或无法判定时只展示真实状态，不安装、不升级，也不阻止 DSH 正常启动。
8. 验收覆盖固定技能交付、子模块一致性、真实路径及版本证据、缺失与探测失败状态，以及只读检查不访问上游、不启动浏览器。通过本地所需检查后，才进入构建交付步骤；本轮不启动正式发布。

以上保留为草案。此前 Q9 的最终确认已撤回；没有开始实现或添加子模块。

## 需求复审

用户提出刚才需求不明确，要求重新判断是否还需讨论。复审确认，前面的提问混用了技能更新检查、技能基准更新和本机安装检查。

- 技能更新检查：判断上游是否有尚未采用的技能变化，不改变子模块。
- 技能基准更新：推进子模块提交，改变下一次交付内容，必须由用户明确发起。
- 本机安装检查：读取 DSH 可调用安装的状态、路径与版本，不安装软件、不判断上游更新。

结合 Q4 已接受的答案，打包检查上游变化并仅提示的行为已有决定，不应重复提问。剩下未得到直接回答的是上游检查失败时是否仍允许打包固定版本。其他已明确的边界继续保留，不重新提问。
