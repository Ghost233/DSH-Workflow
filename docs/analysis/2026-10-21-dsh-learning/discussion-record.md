## 已知事实

- DSH 提供插件启停。平台插件开关作用于整个 profile；即时装卸依赖 HMR，其他配置可能需要重启。
- DSH 的 `session/event` 接口可观察已提交的会话事件。一次 `turn/end` 表示回合结束，任务是否通过验收仍需单独判断。
- DSH 的 skills 注册接口支持独立提供器。文件系统提供器支持专用目录，可用于控制经验的发现与加载。
- DSH SDK 可启动独立会话，并返回会话事件和代理状态。项目任务适配和验证结果判断仍需集成。
- 当前项目的 agent-monitor 只负责检测、通知和记录。JEV 中心提供按名称调用的语义判断入口。
- Harness² 提供根据执行证据提出改动、试跑比较和保留经验的方法。公开执行器为 OpenCode 和 Codex，接入 DSH 需要适配。
- 根测试运行器只自动发现现有几个测试目录。新增插件目录需要明确接入完整测试入口。
- 应用按固定目录复制项目资源，并生成内容摘要。新插件需要同时接入源码启动、应用资源和交付校验。
- 当前 GitHub Actions 只在发布 tag 上运行，没有普通 push 或 PR 测试门禁。现有发布构建不代替本地完整检查。

## 已确认决定

用户在第一轮回答中确认：

- Q2：候选自动生成，由用户查看证据与变更后明确采用。现有 `AGENTS.md` 约束始终作为边界。
- Q3：学习与经验使用按项目分别控制，初始关闭。关闭学习后，已采用经验仍可继续使用。
- Q1 补充：用户在解释完整接入方案后要求“继续”，按推荐将“DSH 独立插件封装原版 Harness² 完整核心”作为首版目标。
- Q4：自动收集开启学习后当前项目的新任务证据。用户明确标记任务完成或失败时启动一轮 Harness²，并提供“学习本次任务”按钮。历史任务手动选择，每轮回复结束不自动重跑整项任务。
- Q5：允许在实验环境中针对任务指导、经验、skills、辅助脚本，以及可映射的工具、子代理和自研插件配置提出候选。现有代理约束、权限、凭据和第三方上游源码保持固定。
- Q6：已采用能力先由插件管理的项目经验库保存和提供。写入项目默认 skills 目录属于单独显式导出。关闭经验使用后停止后续加载，当前会话已读内容保留。
- Q7：优先本机运行，独立 Harness² 组件随 Mac 应用交付，启动时不下载环境。
- Q8：任务试跑、候选生成、选择与反思统一通过独立 DSH 会话执行，实验固定使用来源任务的模型配置，JEV 只辅助局部判断。
- Q9：默认 k=1，全局同时一个学习实验。工程准备好可重复实验环境后才试跑；缺少环境时标为待实验。关闭学习停止新调用并取消或收尾所属实验，保留主任务。
- Q10：以 DSH 工作区根目录隔离开关与经验。不同工作区或 worktree 分别保存，同工作区多个会话共享。
- Q11：配置可用性和相关确定性检查是采用门槛。合法但缺少客观收益标准的候选可由用户人工判断采用，保留相应标记。检查失败或无法映射的候选不可采用。
- Q12：主要通过 DSH 插件公开操作与用户可见行为验收，执行真实核心并使用可控模型响应覆盖完整流程；检查源码与打包一致性。真实模型效果实验单独记录。

## 当前候选方案

以下内容保留方案形成过程。已确认范围以上一节和正式 Spec 为准。

### 接入方式

最初建议开发独立的 DSH 自研学习插件，先采用 Harness² 的改进方法。用户随后追问：独立学习插件与完整接入 Harness² 有什么区别，为什么不完整接入。

这暴露出第一轮选项混合了两个层次。独立插件是 DSH 内的交互与集成形式；完整 Harness² 接入是内部实现范围，两者可以同时成立。最初建议的轻量流程尚未获批，不能据此缩小实现范围。

已确认方案是：用 DSH 插件提供开关和项目采用界面，在外部适配层调用原版 Harness² 核心流程。模型与运行方式已由 Q7、Q8 确认，具体配置映射按实现与验收核实。

### 完整接入的技术核对

源码只读调查确认，原版调度器可以接收外部任务适配器、改进器和选择器。官方 demo 也使用自定义改进器。这为保留原版核心方法、通过外部适配层接入 DSH 提供了入口，无需先修改上游。

“完整核心方法”指保留原版的通用与领域候选提出、试跑、组合、递归模式、结果选择、反思、实验经验库和预算记录。DSH 插件负责开关、任务入口、项目候选和人工采用。原版内部选定结果与项目采用分别记录。

“全部配置组件兼容”是另一项验收。原版提示模板目前只识别 OpenCode 和 Codex 的配置表达。外部适配层可以声明使用其中一种表达作为中间表示，再映射到 DSH；hooks、plugins 和 subagents 的执行语义需要逐项验证。无法映射的项应明确拒绝。

只替换任务执行器，不会自动替换改进器与选择器。原版调度器允许显式注入这些对象，因此可以研究用 DSH 同时驱动任务执行与改进；这需要满足完整响应和编辑文件契约。

官方 benchmark 指南要求 Linux。后续探针已经验证 macOS 上的无模型最小核心流程，DSH 集成与应用打包仍需单独验证。项目环境准备遵守仓库边界，学习功能只消费已准备的运行环境。

当前方案已确定为“DSH 独立学习插件 + 原版 Harness² 完整核心 + 自研 DSH 适配层”。最初自行实现简化流程的方案不再作为首版默认。

插件读取当前项目的任务执行证据，形成改进候选。候选通过验证并被采用后，插件为后续任务提供相关经验和 skills。学习能力不改变模型参数。

Q5 已确认较完整的候选范围。具体组件需要列出映射和验收要求，可靠映射尚未证明的组件不能直接宣称支持。

### 本机环境探针

已调查的 Harness² checkout 提交为 `1cfe254e8d25b15f37048c3730134686abe60335`，工作区干净。主机为 Darwin arm64。当前 PATH 中的 Python 是 `/usr/bin/python3`，版本为 3.9.6。源码未准备 `.venv`，常见安装位置未发现 Python 3.12 或 3.13。

离线枚举已有 uv 解释器时，命令 `UV_OFFLINE=1 uv python list --only-installed` 退出 2。原始原因是 sandbox 拒绝打开 uv 缓存目录中的文件。本次未运行 demo，也未安装、下载或修改上游。

后续使用 `UV_OFFLINE=1 uv --no-cache python list --only-installed`，退出 0，找到现成 Python 3.12.14。随后原版无模型 demo 实际完成，两种模式和两个任务均通过，工作区保持干净。完整命令、版本、退出码与断言见[核心探针](harness2-core-probe.md)。

该结果只证明本机最小核心流程可运行。DSH 适配、模型接入、完整配置映射和应用打包仍独立验收。

### 开关与作用范围

已确认：分别控制“继续学习”和“使用已采用经验”，按项目保存状态，初始关闭。

关闭学习后，停止收集新样本和安排新分析。已安排的学习任务取消或收尾，已保存经验继续保留。关闭经验使用后，停止后续发现与加载。

整个插件的停用仍由 DSH 管理。停用过程应释放插件拥有的资源，并报告真实状态。当前会话中已加载的经验仍属于会话历史，干净对照使用新会话。

### 候选与采用

已确认：候选生成自动执行，正式采用由用户查看证据和变更后决定。候选与已采用经验的具体存储方式仍待确认。

Q6 已确认：学习数据保存在插件管理的项目经验库，通过插件按需提供。直接写进默认扫描目录的 skills，可能在学习插件关闭后继续被原生提供器加载，因此正式项目写回采用显式导出操作。

每项候选建议保留来源任务、修改内容、适用范围、验证记录和版本。失败候选记录原因，避免重复尝试同一方案。

### 验证与模型职责

建议优先复用工程已准备的环境和 Spec/Ticket 中固定的验证命令。模型判断用于辅助评估，业务断言、真实退出码和产物作为验收证据。

生成经验和 skills 的任务由具备生成能力的 DSH 模型会话执行。JEV 用于局部语义判断，现有监控保持检测与告警职责。

实验应排除学习插件自己的运行记录，并记录重复执行、取消和失败的真实结果。后台分析与试跑产生的额外用量需要可见。
