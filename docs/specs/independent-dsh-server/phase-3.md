阶段基准为 `f04ae8be054c3a5ede0abe7686a9cfc4b306619b`，对应已集成的阶段 PR #36。工单为 [S08 #33](https://github.com/Ghost233/DSH-Workflow/issues/33)，正式要求和实时完成状态以该工单及[总规格 #25](https://github.com/Ghost233/DSH-Workflow/issues/25)为准。总交付仍是 [PR #35](https://github.com/Ghost233/DSH-Workflow/pull/35) 达到 ready，由维护者决定合入 main。

## 固定输入与产物

沿用固定 DSH 提交 `1517a4dbca0a2789ff1d41ba439600f8547d23fa`、Node 24.12.0 和 Flutter 3.47.7。源码、锁文件、生成客户端、Matt 构建输入和真实上游 Desktop 适配输入分别记录摘要。最终生产 Wrapper 必须来自干净的已提交源码；早期 source overlay 应用只保留为历史验证，不能替代最终构建。

生产构建与 CI 使用既有 `build.mjs`、`verify-desktop-release.mjs` 和官方 SDK 资源测试。验证包括资源清单、可重定位运行、ARM64、Office、嵌套及外层严格签名，以及外层应用、桌面适配与仓库应用版本一致。固定内核版本和自研插件版本分别记录。记录源码版本和构建输入的一致性，不以 ad-hoc 签名的逐字节相等作为复现标准。

## 真实入口和联合场景

无参入口使用原始 `./start-dsh-workflow.sh` 字节与真实 `/usr/bin/open`。专用 Debug 应用使用现有隔离锚点和完整生产资源，验证真实冷启动、新 PID、自动启动服务及默认插件结果；该证据与 Release 生产构建分开记录。测试资源不替换正常安装，不修改用户登录项。

联合场景使用真实桌面客户端和专用浏览器标签页观察同一实例、工作区、会话和插件状态。Web 单独回收时，原桌面连接、服务和已接收任务继续。随后真正退出客户端与启动器，关闭所有测试业务 WebSocket、流和 HTTP 连接；只通过私有文件门释放已接收任务，再以全新连接重新发现、认证并读取实际持久结果。原生正常退出、清理信号、业务结果和清理结果分别记录。

默认 JEV 与原生监控保持启用。启动插件结果根据真实加载、版本和来源报告；缺包或第三方失败保留原因，不计为已加载，也不阻止其他插件和自研能力继续启动。可用精确版本的实际执行、单项失败后继续、用户停用及未知来源使用自研验收包验证，不修改第三方源码或真实项目锁文件。

## 证据与交付边界

当前负责人、固定候选、有效作业、未关闭问题和原始结果入口为 `.build/independent-dsh-server/controller-state.json`。执行记录包含命令、环境、真实退出码、输入摘要、PID/lease 和清理结果；逐故事映射覆盖规格的 29 条故事，并区分本候选实测、相关输入复用、取消、第三方限制和未完成项。

系统通知、账号、目录、拖放、Office 和更新检查的历史证据仅在相关源码和资源仍有效时复用。整轮失败中的成功子命令保留其原范围；超时、强制清理、缺失证据和跳过均不算通过。真实 macOS 登录、退出登录和重启验收已由用户取消。

CUA 原生应用选择的工具故障另行记录。专用 Flutter/Electron 接口仅在用户逐项授权范围内使用，浏览器仍通过 CUA 操作；工具超时不延长既有验收预算。阶段审查、复盘、必需 CI、集成及本地同步完成后，再执行从总起点开始的双轴审查。此流程不执行正式发布、下载发布资产、安装或切换用户现有服务。
