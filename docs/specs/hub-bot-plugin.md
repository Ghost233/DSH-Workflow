# 中枢 Bot 插件：飞书远程触发与会话状态查询（三层负责人架构）

## 目标

在 DSH Workflow 中交付自研插件 `hub-bot-plugin`，实现三层负责人架构的个人 Bot 体系，**完整学习 dsh-superagent 的机制体系**（状态模型、可靠性、消息纪律、提示词工程、授权），渠道只做飞书。

```
用户（飞书 / DSH 直接聊天）
   │
   ▼
┌─────────────────┐
│ L1 总负责人      │  ◄── 跨仓库中枢，一个常驻 DSH 会话
│  (hub-bot)      │      接收入口消息 → 定仓库 → 注入分派 → 汇总回复
└────────┬────────┘
         │ prompt 注入其会话
    ┌────┴─────────┐
    ▼              ▼
┌────────┐   ┌──────────┐
│常驻 bot │   │动态 bot   │  ◄── L2 负责人：按职责创建的常驻 DSH 会话
│(每仓库1)│   │(实时创建) │      选会话 → 注入或 fork → 汇总状态
└───┬────┘   └────┬─────┘
    ▼             ▼
  会话           会话        ◄── L3 执行会话：普通开发会话
```

### L2 负责人的三类形态

对齐 Codex 的工作目录机制（DSH 原生支持：`createSession` 的 `cwd` 参数，cwd 是会话的身份属性）：

| 类型 | 工作目录 | 仓库 | 用途 | 生命周期 |
|------|---------|------|------|---------|
| **a. 仓库 bot** | 有（仓库目录） | 有 | 像 superagent 一样管理这个仓库：GitHub PR/Issue、分支/worktree、开发任务 | 常驻，每仓库一个 |
| **b. 目录 bot** | 有（任意目录） | 无 | 本地目录工作：私人文档沉淀（旅游规划、笔记）、脚本、临时工程——不公开、不进 GitHub | 常驻或按需 |
| **c. 临时 bot** | 无 → 分配临时目录 | 无 | 即时任务：搜索资料（PTC 模式写脚本需要运行环境）、跑命令、试片段 | **任务完成即自动回收** |

**仓库 bot 的 GitHub 职责（a 类专属）**：
- 执行能力：开分支、提 PR、回复/管理 Issue——作为任务的一部分由 L3 执行会话完成
- 分支/worktree 管理复用 Home Repo 的 `scripts/create-worktree.sh <repo> <issue> <slug>` 约定
- GitHub 事件监听见「GitHub 接入」章节（本版本交付）

- 三类都是普通 DSH 会话，用户可直接打开聊天
- c 类的临时目录由插件统一分配（如 `~/.dsh-hub-bot/scratch/<id>`），目录即会话身份
- 动态 bot（b/c）按需实时创建，注册到负责人注册表
- **创建时机（懒创建）**：插件启动只建 L1；L2 在第一条路由到该仓库/目录的消息到达时才创建，注册表记录"已创建/未创建"，面板可见
- **被删自动重建**：用户手动删了负责人会话（注册表指向已删会话）时，下次注入失败即自动重建并更新注册表——负责人是入口，不允许系统因会话缺失而瘫痪；重建的会话从任务存储恢复在办任务
- **b 类的目录由用户显式指定**（目录即身份，不让 L1 猜）：面板/DSH 里说"给 <path> 建个负责人"，或 L1 反问"这个任务没有匹配仓库，要建目录 bot 吗？目录是？"

**b 类的 git 处理跟随目录现状**：目录已是 git 仓库则利用（bot 改动可 `git diff` 审计、可回滚、可用分支）；不是则不强制 init——目录保持原样。

**c 类回收（全自动）**：任务完成即删除临时目录；注册表保留记录（标 `recycled`），会话历史保留可查。**产物由任务负责带出**——发到飞书、复制到持久目录，或写入产出物清单随报告提交；未带出的随目录删除。回收前 L2 在报告里列出目录内容清单，用户看到有想留的可即时喊停（任务进入 person/review 阶段时才执行回收，验收通过即删）。

### L1 总负责人的落点

- **cwd = Home Repo**：Home Repo 本就是跨仓库协调中心，其 AGENTS.md 的仓库地图即 L1 的仓库知识来源；注册表补充 cwd 映射
- **事件驱动，无轮询**：superagent 每 2 秒跑 Passes 轮询评估；我们不需要——prompt 注入即唤醒会话，所有工作由事件驱动，负责人空闲时不占任何资源

本规格由 Home Repo 地图 [DSH 中枢 Bot：远程触发与状态查询](https://github.com/Ghost233/Ghost233HomeRepo/issues/1) 的决策汇总而成。

## 核心原则

1. **一切皆普通会话**：总负责人、仓库负责人、执行会话都是正常展开的 DSH 会话。用户可以在 DSH 里直接打开任何一个负责人会话聊天；飞书只是聊天的入口渠道之一，核心是会话本身。
2. **注入是第一机制**：通过 DSH 原生 prompt 通道（`dsh-api-session-controller` 的 `prompt()`，消息进入目标会话的 agent inbox）向负责人/执行会话注入消息。注入后的执行与用户在会话里直接发消息无异。
3. **注入还是 fork 是路由选择**：由仓库负责人在仓库内按场景判断，不确定时默认注入（不改变会话拓扑），fork 需显式或确认。
4. **状态驱动**：每个任务有且仅有一个阶段，由"它在等什么"决定。状态摘要是状态的朗读，不是 LLM 的即兴总结。
5. **先存后做**：所有对外动作（注入、回复、通知）先落库再执行，失败重试有保序语义。
6. **消息纪律**：只在人必须行动或结果可用时说话；默认一句话，硬限 100 词；实质工作前确认一次，然后安静干活。
7. **人的优先**：人的消息不被新工作阻塞；人的 pause 跨跟进、跨会话、跨重启保持；自动反馈永不恢复暂停的工作。
8. **bot 即角色，执行透明**（对齐 tbot 思想）：每个负责人是一个有明确角色的会话；与用户的聊天尽量简洁，但底层会话真实执行、过程可见，不隐藏细节。
9. **借鉴 superagent 全部机制，不引入其代码**：事件模型、状态机、Stored work、消息纪律、提示词体系、Policy、恢复语义全部学习；代码自研。
10. **记忆不在本版本**：记忆体系的机制形态未定，本版本不做、也不预留接口。唯一约束：执行会话未来也不用记忆（transcript 即连续性，避免上下文干扰）。
11. **扩展能力外置**：自研代码只落在 `hub-bot-plugin/` 及项目集成层；DSH 与第三方上游保持原样。

## 领域模型

借鉴 superagent 的领域词汇，按个人场景裁剪：

| 概念 | 定义 | 说明 |
|------|------|------|
| **Source** | 事件流（飞书 / GitHub） | 在进域之前丢弃 bot 自己的消息；记录寻址方式（mention/direct）；重启不重放事件 |
| **Trigger** | 一个不可变事件 | 审计与幂等的单位；同一 Trigger 接受两次只产生一个任务 |
| **Thread** | 按时序组织的 Trigger（一个飞书对话 = 一个 Thread） | 同一时刻至多一个评估在跑 |
| **任务（Ticket）** | 一个被授权的工作单元 | 记录授权来源（谁、哪个 Source、何时、哪条消息）——Mandate 的轻量版 |
| **授权记录** | 任务创建时记录的授权上下文 | 每个任务能回答"谁授权的、基于什么"；不可变 |
| **Assignment** | 任务到执行会话的绑定 | 一个任务随时间可有多个 Assignment（重试、恢复） |
| **Channel** | Thread 的写侧（回复地址） | 确认、答案、结果都是写 |

裁剪掉：Mandate 完整机制（scope/strength/revalidation）、Correlation。

## 工具契约（草稿，实现时定稿）

负责人是 DSH 会话，其能力来自插件注入的工具。**工具即权限边界**——会话能做的每一件影响外部的事，都是一个工具调用。

**L1 总负责人工具**：

| 工具 | 作用 |
|------|------|
| `list_owners()` | 列出负责人注册表（含 cwd、kind、会话 id） |
| `create_owner(kind, cwd?)` | 创建动态负责人（b/c 类）；scratch 类自动分配临时目录 |
| `route_to_owner(ownerId, message)` | prompt 注入指定 L2 会话（含授权记录） |
| `query_tasks(filter?)` | 查询任务存储（阶段、仓库、时间过滤） |
| `reply_source(text)` | 经 Outbox 回复触发来源（飞书对话） |

**L2 负责人工具**：

| 工具 | 作用 |
|------|------|
| `search_sessions(query)` | 在自有 cwd 下搜索会话（包装 DSH session_search） |
| `read_session(sessionId, range?)` | 只读会话上下文（包装 session_event_read/trace） |
| `inject_session(sessionId, message)` | prompt 注入执行会话 |
| `fork_session(sessionId)` | fork 执行会话，返回新会话 id |
| `create_session(cwd)` | 在指定 cwd 新建执行会话 |
| `report(stage, note)` | **报告协议**：写回任务阶段（见状态模型） |
| `escalate(text)` | 上交 L1（跨仓库/无法决定/需用户决策） |

**报告协议**：`report()` 是任务状态的唯一写入通道。L2 每个 turn 结束时插件检查在办任务是否有未报告的状态变化；任务从创建到结束的所有阶段迁移都经 `report()` 落库，Outbox 据此通知用户。

## 状态模型

每个进行中的任务有且仅有一个阶段，**由"它在等什么"决定**，从上到下第一匹配行胜出：

| 阶段 | 条件 | 面向用户的说法 |
|------|------|--------------|
| person/answer | 负责人有一个未答问题 | 等您回复 |
| person/confirm | 等待用户确认路由或 fork | 等您确认 |
| person/review | 任务完成，结果待查看 | 等您验收 |
| blocked | 负责人报告无法继续 | 被卡住 |
| failed | 执行失败（非瞬时错误） | 失败 |
| queued | 无空闲执行槽 | 排队中 |
| idle | 执行会话空闲，等待触发 | 待触发 |
| working | 其余一切 | 进行中 |
| done | 验收通过（person/review→accept）或确认取消（person/confirm→cancel）的终态 | 完成 |

- `person/*` 阶段：任务没有人参与就无法继续。**人的消息到达 blocked/failed 的任务会直接释放它**继续执行。
- 实现为九态机（#66）：上表 8 个等待/进行阶段 + 终态 done，idle（待触发）与 queued（排队中）拆分为两阶段；代码以 `src/tasks.js` 的 STAGES/TRANSITIONS 为准。person/confirm 的生产者是确认流程（#69 已落地：fork_session 等重操作先确认后执行）；queued 的生产者是执行槽（#72 已落地：每负责人槽满则排队，槽空按 FIFO 提升）。
- 状态由插件从存储的任务记录计算，`session_event_read` 只用于补充细节；状态摘要 = 状态的朗读 + 必要的上下文。
- 负责人视图（面板或会话内查询）按 superagent 面板三问组织：**有需要我的吗？系统健康吗？这个任务的历史？**

## 消息流

### 远程触发（飞书入口）

1. 飞书消息 → FeishuSource（丢弃 bot 自己的消息，记录 mention/direct）→ Policy 校验 → 落库为 Trigger → 注入 L1 总负责人会话
2. L1 解析意图 → 确定目标仓库/bot（智能推荐 + 用户确认）
3. L1 通过 prompt API 注入到目标 L2 负责人会话
4. L2 轻量 Eval 判断场景 → 创建任务（记录授权来源）→ 执行 → 结果经 Outbox 回复飞书

### DSH 内直接聊天

用户在 DSH 直接打开 L1 或某个 L2 会话发消息，走完全相同的处理路径——飞书只是多一个入口。

### 汇报链（自下而上）

执行层完成任务 → `report()` 到 L2 → L2 **归类总结**（一个仓库/目录内多个任务的状态归并，不只转发单任务结果）→ 上报 L1 → L1 与用户沟通。

- **飞书渠道的回复统一从 L1 出口**：保持单一的消息纪律与跨仓库上下文；L2 不直接回飞书
- **DSH 内直接聊天例外**：谁被问谁答，无中间层
- 结果可用时自动逐级汇报（遵守消息纪律：一句话）；用户随时可问
- **汇报合并**：L2 每次唤醒至多产生一条对外汇报，合并当次唤醒内所有任务的状态变化——连续完成 3 个任务只发 1 条消息

### L2 的四种场景判断

| 场景 | 识别特征 | 机制 |
|------|---------|------|
| 中断恢复 | "继续"、"接着做" | **注入**原执行会话 |
| 状态摘要 | "总结"、"进展" | 朗读状态模型，不写 |
| 简单修改 | "加几行日志"、"小改" | **注入**当前会话（共享目录） |
| 独立开发 | "新功能"、"重构"，或用户显式要求 | **fork**（`sessions.fork()`）或新建会话；涉及隔离时建议 worktree |

默认注入；fork 需显式或确认。

### 跟进消息归属（学 superagent）

- 有进行中任务的 Thread 上，人的跟进消息**直接归属该任务**，不再走评估
- 执行会话处理范围内的跟进，范围外的交回负责人
- **所有归属方都交回，消息才成为新任务的候选**
- **已结束任务的跟进恢复旧任务**（对齐 superagent）：上下文无价——旧任务关联的会话、目录、分支都还在。例外：旧任务关联的 c 类临时 bot 目录已回收（物理上无法恢复），则开新任务

### 并发语义（学 superagent Thread 模型）

- **同一 Thread（飞书对话）的消息串行处理**：新消息到达时若该 Thread 有正在处理的评估/路由，排队等待；用户连发多条按序合并语义（后到的补充先到的）
- **不同 Thread 并行**
- 同一时刻一个 Thread 至多一个评估在跑

### 消息类型范围

MVP 只处理**文本消息**；图片/文件/语音等其他类型回复一句"暂不支持该消息类型"，不进入任务流。

## 飞书接入

### 应用创建：扫码一键创建，权限一次性申请

不手动创建应用、不手动填凭据。使用 `@larksuiteoapi/node-sdk`（≥1.61.1）内置的 `lark.registerApp()`（OAuth 2.0 Device Authorization Grant，RFC 8628）：

1. 插件启动检测无凭据 → 调 `registerApp()`，拿到验证链接
2. 插件面板渲染二维码（或直接在飞书里打开链接）
3. 用户扫码 → 确认页已预填全部权限与事件 → 一次确认
4. 插件拿到 `client_id` / `client_secret`，写入插件配置，初始化 Client 与 WSClient

```typescript
const result = await lark.registerApp({
  createOnly: true,              // 只允许创建新应用，避免误覆盖已有应用
  appPreset: { name: "DSH 中枢 Bot", desc: "DSH 会话远程触发与状态查询" },
  addons: {
    preset: true,                // 保留平台默认模板（含机器人能力），在其上叠加
    scopes: { tenant: [
      "im:message:send_as_bot",  // 发送/回复消息
      "im:message",              // 读取消息内容（含回复所需）
      "im:chat:readonly",        // 读取群信息（群路由与成员识别）
    ]},
    events: { items: { tenant: [
      "im.message.receive_v1",   // 接收消息事件
    ]}},
  },
  onQRCodeReady(info) { /* 渲染 info.url 为二维码 */ },
});
```

- **权限原则：一次性全部申请**。后续版本新增能力时，用 `registerApp({ appId, addons })` 对已建应用增量补权限（确认页展示 diff，重新扫码确认），不手动进开发者后台。
- **例外**：事件订阅方式（长连接 vs webhook）属敏感配置，不能走 addons；创建后插件用新凭据调一次 [更新应用开发配置 OpenAPI](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/application-v7/application-v7/application-config/patch) 设置为长连接模式，自动完成。
- 凭据由上述流程自动落盘到插件 stateDir 的凭据文件（`feishu-credentials.json`，0600 仅属主可读），重启自动重载；用户全程不接触字符串。

### 消息通道

- `@larksuiteoapi/node-sdk` 的 `WSClient` 长连接，主动连接，无需公网回调地址。
- MVP 纯文本交互（候选列表回复数字选择），后续升级交互卡片。

## GitHub 接入（a 类仓库 bot 专属）

对齐 superagent 的 GitHub Source：仓库 bot 盯着关联仓库，**有新的 PR / Issue 自动处理**。

- **轮询模式**：个人场景无公网回调地址，采用 GitHub REST 轮询（认证限额 5000 次/小时，每仓库 5 分钟一次足够；间隔可配置）。凭据复用本机 `gh auth` 已登录身份，不另配 token
- **水位线**：首次对某仓库开轮询只记录当前最新 Issue/PR 编号，**历史存量不触发**；想处理存量需显式指令（对仓库 bot 说"把现有开放 Issue 过一遍"）
- **逐仓库开关**：a 类 bot 默认全开监听，面板可逐仓库关闭（如只读 fork 类仓库）
- **事件范围**：新 Issue、新 PR → Trigger；评论中的 @bot mention → Trigger（mention 寻址）；其余评论按跟进归属规则归入已有任务
- **Policy**：GitHub login 白名单（默认仅用户本人）；非白名单作者的 Issue/PR 只记录不处理
- **身份标识**：轮询复用本机 `gh auth` 身份，bot 在 GitHub 上的产出显示为用户本人账号——因此 bot 产出的所有 GitHub 内容（评论、回复、PR 描述）统一带 `dsh-badge` 标识（"powered by dsh"），与 superagent 的 "This is by an automated agent" 前缀同理，区分人与机器
- **自动处理**（对齐 superagent，直接干不确认）：本人开的 Issue = 显式请求豁免。收到即 ack 一句话回 Issue（"已受理，处理中"）→ 开 worktree → L3 修复 → **提 PR → 经汇报链通知"做完了，请审核"**（任务进入 person/review，验收对象就是 PR；合并永远由人决定）
- **喊停与忽略**：飞书或 Issue 里回复"停"即终止任务（对齐 superagent stop）；带 `bot:ignore` 标签的 Issue 只记录不处理——随手记想法时用
- **源头关闭即终止**：轮询发现关联 Issue 被关闭 / PR 被合并或关闭时，关联任务自动终止并通知你（你可能已经自己处理了——让位于人）
- **永不直推主分支**：bot 的一切代码改动走 worktree + PR，由人合并；bot 账号即使在仓库有写权限也不直接 push 主分支
- 新 PR → review 或 CI 状态跟进（修复并验证的评论静默处理，拒绝的给一句理由）
- **提 PR/Issue 不是特殊流程**：L3 执行会话的正常开发流程自然产生（`gh pr create` 等），插件不为其设计特殊通道
- 与飞书入口走**完全相同的 Trigger → Policy → 任务 → 汇报链路径**；区别只是 Source 不同

## Policy（授权与准入）

借鉴 superagent 的 Policy 思想，按个人场景适配：

1. **授权人白名单**：插件配置维护飞书 user_id 列表，默认只含用户本人；非授权人消息直接丢弃，不进入任何会话。
2. **寻址方式**：Source 记录 mention/direct。群聊中只有 @bot 的消息算请求；私聊消息直接算请求。
3. **显式请求豁免**：授权人直接寻址的消息是显式请求，跳过规则评估直接成为任务。
4. **主动工作从"只记录"开始**（后续版本做主动行为时遵循）：无请求的主动工作先只记录"它本会做什么"，验证符合预期后才放开。
5. **注入会话无审批**：被授权人触发、经负责人注入的执行会话**无人值守执行命令，不弹审批**（对齐 superagent Executor）——远程场景下审批即失效。安全兜底 = 白名单 + 授权记录可追溯 + **危险命令黑名单**（`rm -rf`、`mkfs`、磁盘写类等，配置可扩展，命中即拒绝并回复用户）。
   - 仅"经插件注入链路"的会话享受无审批；用户在 DSH 手动开的会话沿用 DSH 默认审批
   - fork/新建的隔离任务同样无审批（有 worktree 隔离）

## 消息纪律（学 superagent，prompt + 代码双重约束）

负责人会话与执行会话的行为规范：

1. **只在必要时说话**：人必须行动（需要决策/资源/验收）或结果可用时才发消息。
2. **默认一句话，硬限 100 词**（代码强制截断并提示）。
3. **Confirm concretely, once**：实质工作前确认一次——指明对象和预期结果；确认后安静干活，不刷进度。
4. **一次只问一个具体问题**，问题直达用户，不埋在长报告里。
5. **诚实交付**：完成就完成，失败就失败；不确定的不说完成。
6. **让位于人**：人已经自己动手做了的事，不重复做，一句话指出后收手。

## 提示词体系（学 superagent，本次就做）

### 负责人 preset

- L1 与 L2 各有自己的 agent preset（参照 superagent 的 `dsh-superagent-router`/`dsh-superagent-worker` 分工）：
  - **L1 路由 preset**：只路由——一个路由工具一次处理多个候选，路由备注 ≤30 词，不做技术决策；**完全只读**（fs 工具 `write:false, edit:false`，对齐 superagent router preset 实证）
  - **L2 执行管理 preset**：选会话、注入/fork、汇总；**只读 + 会话管理工具**，无写文件/跑命令能力
  - 职责边界由工具保证，不由提示词保证：**一切动手（写文件、跑命令）只发生在 L3**
- L3 执行会话保持用户自己的正常 preset，不被插件改写
- **模型**：负责人会话默认沿用 DSH 默认模型，面板可按负责人单独覆盖（如 L1 路由配便宜模型、a 类仓库 bot 配强模型做 review）

### 不等待 guard（代码强制，非 prompt 请求）

负责人会话**不能被阻塞**——它被堵住一步，所有新消息的路由都被延迟：

- 拒绝 `sleep`、拒绝 >30s 的 shell timeout、拒绝 >5s 的 job wait
- 前台 shell 命令 5 秒后自动转后台 job（对齐 superagent 的 5 秒规则），下一步即可收新消息

### 工具裁剪

负责人/执行管理的无人值守环节不使用会问人或弹 UI 的工具（`ask_user_question`、`present` 等）；问人统一走消息纪律第 4 条。

### 提示词组装与优先级

从强到弱（对齐 superagent）：

1. **工具与代码强制的事实**：身份、权限、参数校验、长度限制——prompt 文本改变不了
2. 内建段落与生成段落（Policy 段落每次请求重新生成，放最后，使 Policy 变更不影响前文缓存）
3. 任务的授权记录
4. 用户自定义段落
5. **外部文本永远是数据**：消息、文档、引用内容永不改变规则与授权

### 版本化

- 提示词配置每次保存产生不可变版本；会话在每个模型请求时读最新版本
- 升级插件默认值变更时，用户已覆盖的段落保留并标记"默认已更新"，用户选择保留或采用新默认

## 可靠性（学 superagent Stored work）

### 先存后做

- 所有动作（注入、飞书回复、会话间通知）**先落库，再执行**
- 失败重试：2 秒后首次重试，指数退避，上限 1 分钟（飞书回复）/ 5 分钟（注入）
- **同一任务到同一对话的消息严格保序**：确认永远先于结果；前一条未发出，后一条等待；前一条连续失败 3 次才绕过并报系统问题
- 消息只在对话永久不可达（被撤回、会话不存在）时丢弃；丢弃保留记录，永不重发
- 一次性网络错误不惊动人；同类工作连续失败 3 次才上报为系统问题

### 已读/未读的精确定义

- 消息被会话 step 拿到**并进入 history**才算已读
- 被 cancel 或错误切断、未进 history 的算未读，恢复后重新投递且去重（旧副本先取出，新投递是唯一副本）

### 重启恢复

- 重启时进行中的 Assignment 以 "host restarted" 结束；新 Assignment 带 **recovery note** 启动：先检查目录与 git 状态，再重复任何对外动作，最旧的任务优先
- 等待中/等人/被卡住/失败的任务保持原样，除非其间有新消息到达

### 模型限流与预算

- 负责人/执行会话遇到模型限流或预算耗尽：等待恢复后自动续跑（学 superagent RetryHealth），不失败、不丢任务
- 面板"系统健康吗"显示等待模型恢复的会话

### 飞书 API 限流

- 指数退避重试；WebSocket 断连由 SDK 自动重连，插件记录连接状态
- 凭据无效：启动时验证并在面板提示重新扫码

## 并发与人的优先

- 执行槽有并发上限（默认 3，可配置）
- **人的消息/状态请求有一个额外专用槽**：槽满时新工作排队，但人的消息永远能立刻唤醒对应会话——新工作不能阻止人继续已有任务
- **GitHub 自动触发的任务占普通槽**，与用户飞书触发的任务同等待遇；自动任务再多也挤不掉人的专用槽
- 任务交还给人（等验收/等回答）时立即释放执行槽

## 记忆系统（不在本版本）

本版本不实现记忆机制，也不预留接口——记忆体系的机制形态（同步查询接口、离线 dreaming、索引加载等）尚未确定，预留任何接口形状都是过早承诺。未来做记忆时重新设计并单独成文。

调研结论存档（供未来设计参考）：
- **只服务 L1/L2 负责人**；L3 执行会话不用记忆（transcript 即连续性，正常开发不加载以避免上下文干扰）。
- 记忆内容（对齐 Anthropic always-on 记忆四类）：user instructions（每 run 必载）、user notes / task progress（索引加载，按需拉取）。
- 原则：记忆只存"无法重新查到"的东西；已在其他系统里的只存指针。
- dreaming（离线整理）为更后续增强。

## 数据模型

**负责人注册表**（插件数据目录持久化）：

```json
{
  "owners": [
    { "kind": "repo", "workspace": "DSH-Workflow", "cwd": "/path/to/DSH-Workflow", "sessionId": "session-l2-xxx", "createdAt": "..." },
    { "kind": "dir", "cwd": "/path/to/some-dir", "sessionId": "session-l2-yyy", "createdAt": "..." },
    { "kind": "scratch", "cwd": "~/.dsh-hub-bot/scratch/01J...", "sessionId": "session-l2-zzz", "createdAt": "...", "transient": true, "recycled": false }
  ]
}
```

`kind` 区分三类：`repo`（有工作目录有仓库）、`dir`（有工作目录无仓库）、`scratch`（无工作目录，分配临时目录，`transient` 标记可回收）。

**任务存储**（SQLite 或 JSONL，插件数据目录）：

```json
{
  "id": "task-...",
  "triggerId": "trigger-...",
  "authorization": { "actor": "ou_xxx", "source": "feishu", "addressing": "direct", "messageId": "om_xxx", "at": "..." },
  "owner": "session-l2-xxx",
  "stage": "working",
  "mechanism": "inject | fork | new | readonly",
  "targetSession": "session-abc",
  "assignments": [{ "state": "running", "startedAt": "..." }],
  "outbox": [{ "to": "feishu:chat:oc_xxx", "body": "...", "state": "queued|sent|failed", "attempts": 0 }]
}
```

**任务历史**即任务存储的已结束记录，供查询与审计。

## 错误场景（面向用户）

| 场景 | 行为 |
|------|------|
| 找不到匹配的仓库 | L1 回复推荐列表 + "其他"，用户回复数字选择；选"其他"时引导创建对应负责人 |
| 仓库内找不到匹配会话 | L2 回复候选列表 + "新建会话" |
| 目标会话正在执行 | 消息进入其 inbox 排队，回复一句"已排队，当前任务完成后执行" |
| 目标会话已删除 | 任务转 failed，回复用户并提供候选会话 |
| 确认超时 | 待确认路由 24 小时未确认自动取消，回复"已取消" |
| 同一任务重复触发 | 幂等：同一 Trigger 只产生一个任务；重复消息回复"已在处理" |
| 飞书凭据过期/无效 | 启动时验证，面板与负责人会话同时提示重新扫码 |
| 非文本消息（图片/文件/语音） | 回复"暂不支持该消息类型"，不进入任务流 |

## 观测性：独立 web 面板

本版本交付插件 web 面板，组织为回答三个问题（对齐 superagent 面板原则）：

1. **有需要我的吗**：person/* 阶段的任务列表，每行直接给出它需要的动作（回答/确认/验收）
2. **系统健康吗**：飞书连接状态、投递失败、凭据状态；健康时占最小空间（安静默认）
3. **这个任务的历史**：单任务时间线（Trigger → 授权记录 → 各 Assignment → 报告 → 回复）

面板原则（学 superagent 005）：
- **安静默认**：健康状态不占空间；问题必须可操作；一次性网络错误不呈现
- **诚实状态**：计数 = 列表长度；状态间不互相矛盾
- **一概念一位置**：设置按概念分组；内部 id 只出现在折叠详情里，能解析成名字的用名字
- **破坏性动作需确认**（停止任务、删除负责人）
- 使用 DeepSeek Harness 设计 token 与控件行为；每个设置块一个保存条，仅在有变更时可见

聊天查询（问 L1）与面板并存：面板看图，聊天追问细节。

## 规模假设与存储

个人场景假设：≤20 个负责人、≤100 任务/天、≤5 并发。存储用 **SQLite**（与 superagent 对齐；事件溯源友好；插件数据目录下单文件）。所有 schema 带版本号，升级时自动迁移。

## 用户功能验收

1. 插件启动后无凭据时展示二维码；用户飞书扫码一次确认后，凭据自动写入、长连接自动建立，全程不进开发者后台。
2. 用户可在 DSH 中直接打开总负责人会话聊天，也可以从飞书发消息；两种入口走同一处理路径。
3. 飞书发送"继续 DSH-Workflow 里那个登录功能"，L1 确认仓库后注入 L2，L2 选中会话并注入继续开发；该会话的事件流与用户在 DSH 里直接发消息产生的无异。
4. "总结一下某仓库的进展"返回的是状态模型的朗读（几个进行中、几个等我、几个被卡住），可逐任务展开历史（从 Trigger 到当前阶段）。
5. 独立开发类指令经确认后 fork 目标会话执行，原会话事件流不变（可用 session_event_read 对比验证）。
6. 非授权飞书用户的消息被丢弃，不进入任何负责人会话；群聊中未 @bot 的消息不成为任务。
7. 负责人会话在执行长命令时 5 秒转后台，仍能接收新消息；负责人会话代码层面无法 sleep 或长时间等待。
8. 对负责人说一句任务指令，它确认一次（指明对象与预期结果）后安静执行，完成后一句话回报；中间不刷进度消息。
9. 插件进程重启后，进行中的任务标 recoveryPending 恢复；恢复注记随恢复后首次注入/追问携带，崩溃前已存未投的注入行重投时同样在文本首行补注记（恰好一次，投递成功才清除标记）；已发出与未发出的飞书消息不重复、不丢失、保持顺序。
10. 执行槽满时，用户对进行中任务发消息仍能立即送达。
11. 每个任务能回答"谁授权的、什么时候、基于哪条消息"。
12. 在关联仓库开一个新 Issue（白名单账号），5 分钟内仓库 bot 受理并在 Issue 下 ack；修复类 Issue 自动开 worktree 由 L3 修复并提 PR，随后经汇报链收到"做完了，请审核"；带 `bot:ignore` 标签的 Issue 不触发；非白名单账号开的 Issue 只记录不处理；任务进行中回复"停"可终止。
13. c 类临时 bot 任务完成并验收后，临时目录自动删除，注册表保留 `recycled` 记录，会话历史仍可查。

## 实现边界

- 自研代码仅落在 `hub-bot-plugin/`；DSH 与第三方上游保持原样。
- 会话操作用 DSH 原生 API：`session_search`、`session_event_read`、`session_trace`、`sessions.fork()`、prompt 注入（`dsh-api-session-controller`）。
- 本版本不做记忆机制（不预留接口），不做微信渠道、实时流式更新、多步骤工作流编排。
- GitHub 侧本版本做：新 Issue/PR 轮询监听 + 自动处理 + review 回复；**不做** auto-merge（合并永远由人决定）。
- 主动工作（无请求的行为）本版本只做"只记录"模式的地基，不放开执行。
- b 类目录 bot 不自动回收；c 类临时 bot 任务完成即自动回收。
- 非文本消息类型（图片/文件/语音）不支持。

## 工作顺序

1. **插件骨架**：创建 `hub-bot-plugin/`，按 `agent-observation-plugin` 的打包方式接入 DSH；实现配置项读取与状态展示。
2. **注入链路验证**：验证通过 prompt API 向既有会话注入消息的最小闭环（这是全部后续工作的地基）。
3. **飞书接入**：实现 registerApp 扫码一键创建（权限一次性预填 + 自动设置长连接模式）→ 接入 WSClient + Policy 白名单与寻址记录，验证飞书消息 → 注入 L1 的闭环。
4. **领域核心**：Trigger/任务/授权记录存储、状态机、Stored work + Outbox 保序重试。
5. **提示词体系**：负责人 preset（路由/执行管理）、不等待 guard、消息纪律、工具裁剪、版本化。
6. **L1 总负责人**：意图解析、仓库路由、负责人注册表。
7. **L2 负责人（三类）**：会话选择（四种场景）、注入/fork 执行、状态汇总、跟进归属。
8. **恢复与并发**：重启恢复（recovery note）、已读/未读语义、执行槽与人的优先槽。
9. **GitHub Source**：轮询监听 + 新 Issue/PR 自动处理 + Policy login 白名单，验证 GitHub 事件 → 仓库 bot 的闭环。
10. **Web 面板**：三问组织的最小面板（需要我的/系统健康/任务历史）+ 设置页（白名单、危险命令黑名单、并发上限）。
11. **验收**：按「用户功能验收」逐条在真实 DSH Web 中核对。
