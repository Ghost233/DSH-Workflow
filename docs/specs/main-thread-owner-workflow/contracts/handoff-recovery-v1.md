# 失败handoff的实际Planner预算入口（R59）

适用于显式recovery协议下、已批准active版本中真实失败Owner的handoff。recordHandoffs在最新状态事务中记录sourceExecution：合同DSH_HANDOFF_SOURCE_EXECUTION_V1、planDigest/taskId/ownerId/attempt/sessionId/reportStatus/commitSha；requestHandoff也固定对应live执行身份。该记录只证明生产来源，实际领取仍要求同一Owner执行已经failed/blocked且通过R57来源/审批/权限/continuation核验。生产时completed partial报告保留completed及commitSha，不能假冒失败来源。

实际replanHandoffs首先校验recovery状态。缺少来源的旧pending项拒绝猜测免费或恢复路径；存在失败来源时进入replanRecoveryHandoffs。正常completed handoff沿既有正常路径，不制造恢复root。本轮没有证明正常路径跨版本预算激活，亦没有补齐verification重开触发来源；这两项仍待后续处理。

失败项按相同sourceExecution拆组，按handoff ID确定第一组。一次候选仅消费一个来源，不拿一个root支付其他Owner的独立问题。operationId固定于origin及handoffIds；完整组内容另行冻结，改文字不产生新的操作身份或重送许可。最新来源和完整组在执行前及应用前核对。

准备时持有规划入口资源租约，仅在短workflow事务中将R57预算预留与DSH_HANDOFF_REPLAN_OPERATION_V1一起保存。操作记录固定origin/组/ordinal/requestId/prompt/base Git事实/parent版本/phase。外部Planner调用通过R58真实会话适配器，期间不持workflow锁；独立状态更新可继续。running、unknown、cancelled不得换ordinal重试；明确failed后下一实际调用领取连续ordinal，共用原root及Workflow有限额度。拒绝领取不调用模型。

实际提交后复核live Registry、Git head/branch/status、当前来源与父版本，再在最新状态事务中使用既有handoff语义检查：保留已完成或有运行现场的任务、禁止repair依赖未完成失败源、目标Owner覆盖全部交接文件。另限制本组来源task/覆盖文件的目标task之外既有task原样保留，新增任务只属于本组相关Owner。

语义有效时在同一事务保存pendingPlanRevision与T13 succeeded，session phase=applied。候选保留recoveryRequestId/recoveryOrigin/handoffIds，active plan、active digest、tasks与Owner runs不被覆盖。语义无效时同事务保存失败原因/T13 failed，phase=validated_failed；无结构提交时沿R58终态失败结算。所有情况均不退款，不关闭根问题。

候选重放重新核对operation身份、session记录、账本引用、原始完整JSONL receipt以及pending candidate digest；新Harness上下文也不调用模型。若输入或来源在执行中变化，只暂停并保留已用预算，不写过时候选。candidate_staged只证明规划产物持久化，不是Review通过、用户业务决定、版本激活或最终问题关闭。

后续必须让candidate Review继承此origin并单独计费，连接咨询、候选重建与T18版本激活；Runner技术暂停报告也需覆盖这些实际入口。当前不能声称完整端到端无人值守验收通过。


## R60 直接请求保留来源与真实终态

显式恢复协议的request_handoff核对active Owner与持久记录的attempt/session/planDigest/leaseToken，只允许当前实际执行者请求。仍用applyPlanDelta计算和校验候选，拒绝非法Registry、completed失效等，但不把计算结果写入active状态：source Owner、task/slot、supervisorOutbox、plan/digest/review/approval与workflow running均保留。

提案固定为DSH_HANDOFF_DELTA_PROPOSAL_V1（basePlanDigest/plan/invalidate/carryForward）附在handoff；Planner提示明确其未应用，必须独立校验。工具返回proposalOnly与后续提交blocked/failed报告的指引，不宣称当前Owner已终止。主控制看到与当前active记录匹配的live直接handoff会等待handoff_source_running；admission仍拒绝running来源，不能提前消费预算。

只有runChild真实结束，现有失败收尾才保存Owner blocked/failed和task stopped。存在同版本、同attempt/session且无partial commit的固定handoff时，实际非完成报告（包括报告重复携带handoff）是受控技术交接；已付费Owner可按原session/prompt结算failed并保留continuation，后续Planner同root另付一次。技术blocked不再自动变成await_user，但真实typed user authority继续优先投递主线程，handoff不豁免权限门禁。

本轮真实Harness测试覆盖免费Owner、已付费Owner、报告重复handoff和真实typed permission gap；以实际request_handoff/owner_submit、原始JSONL终态和后续Planner提交验证，不人工伪造terminal。非完成报告的技术结算不是commit成功或问题关闭。没有来源绑定的异常、未知执行、正常partial commit及跨版本状态均不获得本补丁的自动结算许可。


## R61 completed提交门禁与反向并发窗口

owner_submit的completed路径在active.submitting=true后、inspect/固定验证/commit之前调用assertOwnerCompletionAdmission。Runtime在workflow短锁中读取最新状态，对受保护执行核对协议、实际Owner lease、active plan内容/digest、task运行状态和Owner attempt/session/leaseToken。相同task/Owner仍有pending request_handoff时拒绝completed；来源失配的遗留pending请求也必须对账，不静默忽略并完成。

拒绝仅返回工具错误，finally清除submitting，不写active.submission；同一真实Owner可随后提交blocked/failed并沿R60真实终态及预算继承继续。真正的权限依据仍由原有submission前置分类优先处理。

反向窗口也被封闭：request_handoff在workflow锁内拒绝active.submitting或已有active.submission的Owner，不能在completed已通过门禁后加入新提案。该限制也保护既有非恢复请求的提交次序。未出现pending直接请求的普通完成继续正常检查、验证和固定提交。

真实测试覆盖免费/paid Owner错误completed工具回执、检查/验证/commit均零调用、同会话blocked后Planner继续，以及普通completed检查执行中调用实际request handler被拒绝。它们不代表其他未接线的Review、版本激活或完整工作流已通过验收。
