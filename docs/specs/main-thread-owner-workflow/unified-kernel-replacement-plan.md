## 1. 修复目标与现场依据

目标：需求与 Spec/Ticket 由主线程统一组织；Owner 对模块长期负责；DAG 表达交付依赖；确定性执行内核负责准入、推进、恢复和状态；Runner 驱动执行。用户只参与需求、业务取舍和真实权限决定，不承担日常巡检或每轮批准。

本次诊断的现场是 Coinhub 工作流 `wf-mtytv0hv-f4ee79f0`：12 个任务完成 0 个，T1 停止、11 个等待；Owner 最后调用 `owner_submit` 后没有对应返回；持久原因是 `hard_deadline`，后续进入 `technical_pause`。当时内核投影为 `command: null`，Runner 跳过；Dashboard 缺少技术暂停分支；通知标为 delivered，根会话日志没有相应报告证据。以上是诊断快照，实施前需重新核对，不能假定现场从未变化。

已核实的实现接缝：

- `src/workflow-state.mjs:deriveWorkflowControl` 与 `src/external-runner.mjs:discoverRunnableWorkflows`：暂停后的唤醒缺口。
- `src/runtime.mjs:awaitSupervisorEvent`：恢复对账依赖等待调用；读取/等待承担状态推进副作用。
- `src/runtime.mjs:deliverMainOutbox`：投递接口返回后即记录 delivered，未统一证明根会话持久接收。
- `src/runtime.mjs:executeOwnerSnapshot`：每个固定验证准备新快照，提交调用长期占用 Owner 回合。
- `src/dashboard.mjs:dashboardWorkflowWaitItem`：部分非终态没有对应视图。
- `src/owner-boundary.mjs` 和 `index.js` 的 Owner 指令：最终 diff 审计不能单独满足逐次写入保护合同。
- `index.js` 的 `workflow_planning_configure_default_identity`：自动补写 Git 身份与当前“不得改配置”的约束冲突。
- `test/fixtures/recovery-session-fixture.mjs`、根 `package.json`：测试 TS 加载入口不统一；不能用收集失败评价生产恢复行为。
- `start-owner-workflow.sh:wait_for_web_host`：端口响应没有充分绑定本次宿主实例，测试可能共用用户端口和日志。

## 3. 最终模块划分

不增加独立调度服务、通用消息平台或数据库。将现有插件整理为以下实现，每个职责只有一个生产入口。

| 模块 / 计划文件 | 唯一职责 | 外部接口 |
| --- | --- | --- |
| `src/workflow-engine.mjs`（新增） | 规范化模型、状态转换、准入、预算、计划切换、状态视图 | `transition(state, event, now)`；`view(state, workflowId)`；纯函数，不调用 DSH/Git/文件系统 |
| `src/workflow-store.mjs`（新增） | 原子读取更新、版本冲突、动作领取、内容引用、控制记录持久化 | `transact(event)`；`readView(workflowId)`；内部调用同一 transition |
| `src/workflow-effects.mjs`（新增） | 领取并执行已保存动作，收集事实，报告结果 | `execute(action, signal)`；`observe(action)`；结果必须有身份与证据 |
| `src/submission-pipeline.mjs`（新增） | 候选封存、固定验证、审查、串行集成、原始历史封存 | 作为 effects 的内部实现，不拥有第二套调度循环 |
| `src/runtime.mjs`（替换实现） | 注册工具、提供真实调用者身份、接收 DSH 事件、调用 store/effects | 保留需要的用户工具名称；删除内嵌决策和自行更新状态的分支 |
| `src/external-runner.mjs`（替换实现） | 单一执行驱动、事件唤醒、到期检查、宿主接线 | 只消费规范动作与 nextWakeAt，不读 reason 字符串选择恢复策略 |
| `src/dsh-execution.mjs`、`src/owner-team.mjs` | 使用 DSH 公开能力，管理真实 Agent/Session/工具和终止证据 | 复用并收窄现有适配器；不自行决定任务完成 |
| `src/dashboard.mjs`、客户端及自研消费者 | 展示规范只读视图、发送有身份的交互事件 | 不读旧私有字段计算运行/卡住/完成 |

`model.mjs`、`registry.mjs`、规划来源、公共 Owner 决定、验证、Git、Memory 的有效领域校验保留为内部实现。删除的是重复权威和旧控制路径，不是 Owner、证据和授权保证。

内部协作过程固定为：接收事件 → 原子更新事实和动作 → 提交事务 → 在锁外执行动作 → 以同一入口接收结果。任何长命令、模型调用、审批等待或会话读取均不得持有状态事务锁。

## 4. 持久模型与事务选择

### 4.1 一个控制真源

以现有 Runner catalog 为本机管理单位，在其自研 `.dsh-workflow/` 下建立一个版本化控制记录 `control-state.json`，保存受管项目的活动 Workflow、Attempt、待执行动作、Owner/资源占用、预算和待决事项。该记录是新引擎唯一可变控制真源，使用跨进程锁和原子替换；同一事务中完成状态变化、资源预留与动作登记。

规划快照、候选内容、日志、完整验证输出、Owner 原始历史继续保存为独立不可变产物。先完成产物持久化，再在控制记录中提交引用。中断留下未引用产物可清理，不得出现已引用但未持久化的“完成证据”。历史大对象不装入控制记录，必要去重身份和未结算资源不得因日志裁剪被移除。

单机使用一个有效 catalog 执行者。各项目建立只用于归属校验的 catalog 绑定，真实路径归一化后拒绝第二个 catalog 接管同一项目；不能因根路径别名获得第二组 Owner 锁。绑定与旧数据导入一起处理，不改变 DSH 全局配置。跨项目独占端口等资源使用 host 命名空间；模块与项目内资源使用 project 命名空间。

写入使用同目录临时文件、文件持久化、原子替换和可用的平台目录持久化措施；明确承诺范围并用进程崩溃测试验证。锁归属绑定宿主实例与随机 token，不能仅凭 PID 或锁文件年龄夺锁。磁盘写失败时不执行未持久化动作；文件损坏时保留现场并明确失败，不以空状态重新初始化。已有格式校验、备份核验与原子写能力集中复用，不能再散落到每个调用者。

这项选择用于消除多文件之间的“工作流已派发但资源未预留”窗口。需要监测控制文件体积和事务时长，但本次不建设分布式存储或后台数据平台。

### 4.2 核心记录

| 记录 | 必备事实 | 禁止承担的职责 |
| --- | --- | --- |
| Owner | 项目身份、Registry 版本、scope、模块合同、原始历史引用 | 不等同于某个活动 Session，不从历史推导新权限 |
| Task | 稳定节点 ID、Ticket/AC 引用、定义摘要、依赖产物、Owner、write、resources、固定验证、当前 Attempt 引用 | 不与 OwnerRun 各维护一份可竞争的 running/completed |
| Attempt | 唯一 ID、taskDefinitionDigest、输入产物、授权代次、Session/prompt、工作目录、阶段、动作和结果引用 | 不靠全局 revision 判断自己的结果是否仍有效 |
| Action | 唯一 ID、Attempt 或规划请求归属、类型、参数摘要、领取者、派发/结果证据、下次观察时间 | 不把投递成功当业务完成 |
| Decision / Notice | 稳定 ID、正确根会话、对应请求版本、种类、投递/接收/处理事实 | 技术通知的接收状态不决定任务是否可以恢复 |
| Issue / Budget | 稳定问题来源、关闭条件、证据、已用额度、重试继承关系 | 不因改标题、拆节点、重启或重新规划清零 |

全局 `revision` 仅用于状态事务并发。任务适用性由定义、输入、授权绑定决定；审批、验证和候选各绑定自己的内容摘要。相关来源改变才失效，无关心跳不使已有结果失效。

### 4.3 生命周期

- Attempt 阶段：`dispatching → executing → sealing → verifying → integrating → succeeded`；失败/取消进入 `stopping`，确认结算后进入 `failed/cancelled`。
- 只读会诊、Planner、Reviewer、通知和摘要沿用相同 Action 的领取、观察和终止机制，但各自保留输入/结果校验，不创建专用恢复引擎。
- 已有独立 Operation 也使用相同 Action 生命周期和准入；保留其显式授权与用途，不为一个直接操作强制生成无关业务 DAG，也不留下能绕过 Owner/资源限制的直通入口。
- Task/Workflow 的 ready、running、waiting、failed、completed 为事实投影；不允许客户端直接设置。
- 等待记录统一表达 `reason + responsibleParty + resumeCondition + nextWakeAt/decisionId`。技术等待必须有检查期限；外部决定等待必须有持久请求和可见入口。
- 终止不明达到观察预算后，形成明确技术失败并保留隔离占用；不得标取消成功或重新授予同一写权限。遗留占用的低频核查属于清理义务，不重启已耗尽的实现尝试。
- 完成分为候选接收、任务集成、Workflow 最终验收三个证据层次，不能互相替代。

### 4.4 终止与写入证据的明确边界（2026-09-13 用户确认）

用户在说明 macOS 原生进程范围限制及调整方案后要求“帮我继续调整修改”。据此保留 macOS 和原配置，使用 DSH 公开的托管进程范围保证；不要求任意命令创建的所有逃逸后代均被消灭，不修改上游源码、不增加另一套进程管理服务。

- 命令回执使用 `managedRangeStopped + terminationScope=dsh-managed-range + terminationId`，只证明原生 provider 管理的范围。该范围在 macOS fallback 下不包含所有逃逸后代；`enforcement=full` 是沙箱事实，不能证明全部后代停止。
- Action 的 `executionSettled` 表示其受控执行已结算，不表示业务通过。Owner 进入封存或释放写资格还必须有独立 `sourceWritesClosed`：持久冻结旧授权，并在同一原生修改工具锁上等待所有在途写入返回。
- Owner 的任意 shell 保持只读，修改经受控原生 write/edit；可写安装与固定测试在各自独立目录。目录隔离用于减少互相污染，不作为进程死亡证明，也不改变原有沙箱和审批设置。
- 取消、崩溃和未确认派发仍按第 5 节有限对账，额度到期明确失败并保留相关隔离占用；旧回执、PID 消失、模型回合结束不能直接释放资格。无关任务继续执行。
- 候选内核控制合同升级为 V2，拒绝自动沿用 V1 的混合 `writersStopped` 事实。命令与原生 Session 恢复同样核验新回执；用户现场状态保持原样，原有显式导入要求仍有效。

KAC-10/11 中的终止验收据此分别检查受控写权限关闭、托管范围停止及未知状态收敛；新增真实 macOS 逃逸后代测试，必须证明回执不承诺全部写入者停止。KAC-21 的 Owner 实际越界写入拒绝、候选内容绑定及最终交付标准保持。

## 5. 调度、唤醒与收敛规则

1. 所有动作在一次准入事务中核对：有效计划与来源、前置产物、Owner、路径/资源、并发容量、授权与预算。工具直调与 Runner 派发均进入此事务。
2. 资源一次性按规范顺序领取，不能持有一部分资源等待另一部分。跨 Workflow 的同 Owner 互斥；只读公共 Owner 判断沿用既有与同 Owner 写任务互斥合同。
3. 正常事件立即唤醒；Runner 在启动及定时检查时扫描所有未结算 Action 与到期等待，包含 technical pause。最近 nextWakeAt 驱动定时器，定期有界扫描补漏。
4. 默认补漏间隔上限 30 秒，短暂观察从 5 秒退避到 30 秒；使用可注入时钟测试，不新增用户启动参数。测试应测量约定上限内实际被唤醒，而不只断言字段存在。
5. 没有新事实的检查不增加业务 revision、动作序号或恢复额度。进程心跳与交付进展分开；日志使用有界摘要，不制造 inspect/ack 自激循环。
6. 恢复模型调用沿用现有合法冻结预算；新计划默认采用既有总额度 12、单根问题 8，不另造各模块预算。已配置的合法值不被静默改写。底层相同 Action 的对账不消耗新的模型尝试，但自身必须有超时/观察上限。
7. 执行时间计入准备、模型和验证的实际活动时间；真正等待用户时暂停活动计时，保留授权/资源事实。每条固定命令仍有独立超时，不能靠心跳无限延长总执行预算。
8. 机器重启/时钟回拨不得增加剩余额度；保存剩余上限，在进程内用单调时间测量，在重启后保守计算。
9. 有依据的预算内实现修复沿原 Task 新建 Attempt；无进展或额度耗尽形成失败报告。通知失败独立重试，不阻止安全技术恢复，也不触发产品决定。
10. 一个任务失败不全局冻结无关就绪任务；其消费者明确等待失败前置。无可推进独立任务且问题已不可恢复时，Workflow 明确失败。

## 6. Owner 提交与交付流水线

### 提交接口

`owner_submit` 返回版本化接收结果：`submissionId`、`attemptId`、`status=accepted`，并明确“候选已接收，尚未完成验收/集成”。重复相同提交返回相同身份；同一身份不同内容拒绝。blocked/failed 提交表达偏差事实，由内核决定后续动作，不伪造成功候选。

接收时冻结提交清单、关闭该 Attempt 的修改工具授权并等待在途修改返回；原生命令按第 4.4 节托管范围结算，登记 sealing 动作，然后结束长调用。文件内容封存期间使用固定目录与可核验摘要；未冻结写入不能声称候选不可变。封存失败可恢复，不让 Owner 再次猜测提交状态。

### 候选与验证

- 快照绑定真实源码，包括授权范围内未提交内容；路径审计覆盖新增、删除、重命名、符号/硬链接和忽略文件的保护要求。
- 每个候选只建立一次不可变源码来源。Workflow 不识别语言或包管理器，不安装、缓存、复制、挂载或摘要工程依赖；worktree 的工具链、依赖和构建缓存由工程初始化负责。
- 各验证使用独立可写执行目录并执行 Spec/Ticket 固定的命令。取消后停止受控命令，确认终止再清理本次临时目录。工程环境缺失作为真实执行失败反馈主线程，不由 Workflow 临时修补。
- 固定验证区分文档/基础设施就绪、模块场景和最终集成；不能在未来场景尚不存在时要求上游通过最终验收，也不能用空测试通过上游关卡。
- 候选审查与固定验证必须绑定同一内容。测试结果区分通过、断言失败、加载/编译失败、超时、取消、跳过、零用例、未运行和阻塞。
- 候选有效结果重启后复用；命令或输入变化必须重新验证。单项失败仍收集其他独立验证。

### 集成与 Memory

- 每个项目的集成动作串行，绑定 expected base、候选、合并策略和预期来源。
- 在独立集成候选验证必要组合；共享基线已变化时重新组合并重验受影响项，不能把独立分支通过当组合通过。
- “Git 已更新、状态未写完”通过预登记动作与提交/树证据恢复；核实成功后只登记一次。不盲目 cherry-pick、重提或移动用户分支。
- 原始修改理由、版本、审查与验证引用封存后方可结算任务。摘要可延后，使用普通 Action 重试；摘要失败不撤销有效代码，也不从缺失来源补造历史。
- Workflow 最终验收绑定同一集成候选、全部任务结果和所有业务 AC。只在本地授权范围内交付，不扩展到推送/发布。

## 7. 写入隔离、停止和 DSH 接入

- Owner Team 长期身份保留，活动 Session 可重建；公开 DSH Agent/SessionHandle 是唯一会话接入方式，不手写或修复上游 Session 文件。
- Owner 的原生 write/edit 在实际调用前校验 task.write、Owner scope、保护路径、路径身份和当前授权代次。最终 diff 审计保留为第二道检查。
- 任意 shell 不能依靠字符串识别实现路径隔离：在公开沙箱能力中施加实际写范围；无法保证的命令走自研受控命令入口，由固定目的和原生审批限制。测试脚本也不能绕开范围。
- 禁止通过缺少公开能力就默认开放 shell。若目标 DSH/平台无法实施所需隔离，形成带复现的兼容阻塞，此候选不得以降级保护通过验收；适配在自研代码完成。
- 每个活动命令记录宿主实例身份、Attempt/Action 和可核验进程归属；停止应覆盖其受控子进程。PID 单独存活/消失、心跳过期、取消请求返回、模型 turn/end 都不足以单独证明所有写入者已停止。
- 只有有效授权代次可继续工具写入、提交、合并和写原始 Memory。旧执行回执作为历史保存，不得修改新 Attempt。
- 权限决定绑定精确命令/内容、目录、Attempt 和授权代次。内容变化或计划切换使相关旧审批失效；不得默认全部同意或全部拒绝。
- 删除自动补写 Git 身份的工具和提示词。已有身份正常使用；缺失时报告确切缺失项并等待必要配置决定，不自行写入默认值。

## 8. 主线程、Spec/Ticket、公共 Owner 与改图

- 普通讨论、仅 Spec、完整实施三种授权分别处理。授权完成开发后不再在 Spec/Ticket/DAG/每次恢复之间增加人工门禁。
- 主线程仅在既有受限文档路径写入，保留原生来源、修改者、版本和 checkpoint 校验；控制 JSON、治理文件与代码权限不因此扩大。
- Ticket 保持完整业务 AC，可以展开多个单 Owner 执行包；每包明确产出、前置证据、write/resources、固定验证及偏差条件。
- 编排预检检查数据依赖和验收产物依赖，未来入口必须有生产者。不能凭 JSON 无环认定契约就绪。
- 公共 Owner 请求与决定保留来源、版本、消费者完整性、兼容/迁移/拒绝/补事实结果；本次只统一其 Action 生命周期。公共 Owner 独立判断，下游不能直接授予变更权限。
- 技术修复由主线程在已有授权和预算内处理；产品承诺/范围/真实权限改变才问用户。不根据错误文本中的“用户”等词决定授权类型。
- 已启动的 Task 定义固定。改图先停止向受影响范围派新工作并使旧授权失效，等待相关执行安全结算，再原子启用新版本；无需停止无关任务。
- 父版本 CAS、冻结规划来源、Registry、执行包和问题预算在同一激活事务更新。后到反馈保留。被删除/替换的任务归档，不从旧恢复记录重新生成。
- 未解决义务不因 Reviewer passed、遗漏、改名或拆节点消失；关闭必须绑定真实证据或有来源的替代决定。

## 9. 通知、审批和界面

通知采用一条持久 Action 路径：pending → 接口接收证据 → 根会话持久接收证据；需要业务回答时再记录对应 Decision 的处理结果。普通状态报告不要求模型专门回复确认。

发送前校验 workflow 根会话身份及当前真实 Agent；不得把调用者默认当根会话。使用稳定消息 ID 重放和查询，DSH 没有承诺去重时先查已持久化消息，不能假设相同 ID 天然幂等。Agent.followup 返回不等于 delivered。

根会话离线时保留待投递报告，Dashboard 直接从控制事实显示问题；不创建替代根会话绕过身份。需唤醒主线程的技术偏差通过真实根会话处理，不让 Runner 编造主线程决定。

统一视图必须包含：任务/阶段、真实进展、等待原因、负责推进方、下次检查或待决 ID、最后交付证据、恢复预算、技术失败与残留占用。`actionRequired=false` 只表示无需用户决定，不表示工作正常或已完成。

Owner 客户端、Synapse、SoL、自研审批使用公开视图和事件合同；逐一更新工具结果 schema、Agent preset、提示词及生成的客户端包。SoL 的动作融合不能合并提交接收和验收完成，也不能吞掉失败事实或批准请求。第三方代码不改。

## 12. 旧状态处理与一次切换

本节是当时针对旧 Coinhub 现场的历史迁移方案。用户已取消该任务并归档活动记录，当前不执行下列导入步骤，也不以其作为新任务的验收前置条件。未来若需要迁移其他旧状态，须按当时现场另立规格和证据。

新版不运行旧执行协议，不提供在线双轨兼容。提供一次性、可重复核验的导入工具；它不是日常启动参数，也不是第二套恢复引擎。

| 旧现场 | 导入规则 |
| --- | --- |
| 已完成历史 Workflow | 保留原证据与只读历史标签，不继承为新候选验收通过 |
| 未启动且来源齐全的任务 | 导入 Task/来源/授权/预算，经过新准入才可派发 |
| 已有有效候选/验证/集成证据 | 校验真实内容与来源后导入对应阶段，不重复执行已证明的副作用 |
| 运行中、stopping、termination_unconfirmed | 先停旧派发并核查真实执行者；没有终止/隔离证据就禁止新版获得同 Owner 写权 |
| 来源、版本或副作用结果不明 | 保存为可见导入阻塞，列出缺失证据；不清空、不猜测 completed、不创建重复 Workflow |

切换步骤属于同一次交付的运行操作：

1. 记录当前源码候选、服务实例、旧 Workflow/Agent/进程身份以及自研状态摘要；保护用户原始文件和配置。
2. 全量构建、静态检查、接口/故障测试通过后，停止旧引擎新增派发。只处置已核实属于本次切换的进程；不得按端口或名称批量关闭。
3. 导入工具先生成只读预检报告；源文件原样保留，生成校验过的自研状态备份及新记录。若源状态变化或执行者未结算，停止激活并报告。
4. 以原子激活标记启用新版，拒绝旧协议/旧代次写入，确保一个有效执行者。新执行者启动时先完成所有未结算 Action 对账，再接受新派发。
5. 使用原有配置和无参数入口启动需要切换的本次宿主，复用现有浏览器页面；执行真实联合验收。刷新页面不构成验收证据。

若激活前失败，旧现场保持原样；若激活后已发生新副作用，不能直接把旧状态备份覆盖回去。保留新状态，修复同一候选并对账，禁止通过回退状态制造重复执行。

Coinhub 当前测试必须纳入导入验收。它当时的 `owner_submit` 无返回不能直接视为已封存候选；先确认写入者结束，再核验工作目录、来源和实际内容。能恢复的有效产物保留，不能证明的部分明确重新验证。

| KAC-17 | 已有无关服务占端口/本次宿主退出 | 启动失败准确；就绪绑定本次实例及自研插件加载；日志不覆盖用户日志 | 启动进程集成 |

| KAC-19 | 导入旧 Workflow/切换时中断 | 源数据保留、身份和预算不丢、旧未知执行者不重派、一个生效引擎 | 脱敏旧状态 + 导入中断 + 真实现场核验 |

状态测试与真实执行证明分开记录。纯测试可使用明确标记的 fake；终止、持久接收、权限、集成和最终模型工作流必须有真实证据，不能用 fake 覆盖宣称通过。

## 15. 验收执行与证据要求

- 在本次改动中提供一个自研统一入口 `npm run acceptance:kernel`：覆盖本计划固定集合，产生机器可读结果与报告，失败返回非零。入口是计划新增，不声称现在已经存在或通过。
- 根 `npm test`、客户端构建/检查、自研插件集成和启动回归同步更新，使用一个明确、可重复的 TS/ESM 测试加载方式；只修改自研夹具/脚本，不修上游辅助文件。
- 集中入口消费同一候选清单：实际源码内容摘要（包括未提交变更）、官方 DSH 当前固定版本/指纹、自研插件版本、规划合同、测试清单和环境条件。
- 确定性测试使用测试专用目录、临时端口、进程身份及日志；不伪装成用户 DSH_HOME 的替代生产现场。真实验收使用现有真实配置与模型；凭据只由原程序读取，不进入报告或摘要原文。
- 报告分别列出通过、失败、阻塞、未运行、跳过及取消。所有原 AC 和 KAC 必须映射证据；旧实现被替换的测试必须映射到新用例，不能只 skip 后计作完成。
- 同一候选覆盖至少一次完整正常运行，以及矩阵内中断后的恢复与交付；“故障后安全失败”只证明失败路径，不能替代应恢复成功场景的完成证据。
- 真实工作流包含 Spec/Ticket、公共 Owner 判断、至少两个独立 Owner 并行、依赖解锁、提交/验证/合并、主线程反馈和最终验收。Coinhub 既有测试作为现场回归；修正其验收依赖时保留需求与变更理由，不降低最终 AC。
- 原配置、上游源码、用户未提交内容、服务归属与遗留进程在结束时核对。若宿主能力或现有环境使某项无法证明，列为阻塞，不更改配置或省略该项获取绿色结果。
