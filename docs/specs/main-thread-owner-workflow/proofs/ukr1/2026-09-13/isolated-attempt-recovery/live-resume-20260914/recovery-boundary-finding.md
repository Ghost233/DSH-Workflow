# R10 恢复实机复现：验证边界与自动恢复不一致

本轮是在摘要身份修复已通过 21 项定向测试并重启加载后，用户询问“那么现在是继续尝试？”而启动。没有修改用户配置、需求文档、活动 DAG 或恢复预算。

## 已验证成功

正式 `workflow_replan` 受理相同 R10 和批准的 Registry baseline。Planner 省略 registryDigest 后，Runtime 正确绑定；第一次局部校验拒绝多出的 browser_harness_smoke，Planner 在同会话纠正，结构化计划成功发布到独立审查。与旧 DAG 相比仅 2 个任务字段组和 browser_harness_tooling.run 变化，未受影响定义保留。修复前的摘要问题没有重现。

## 新失败链

1. 初始恢复边界包含 9 个浏览器相关任务，但验证清单只包含 browser_harness_tooling。这不足以落实 R10 下游 wrapper 的真实调用要求。沿用该边界时没有一次性补齐两个下游验证项，是本轮恢复准备的缺口。
2. 独立审查准确指出 panel_browser_producer 与 host_parity_browser_producer 仍直接执行 npm exec playwright test，绕过首次加载 Playwright 前设置环境的 wrapper。该问题是执行合同缺口，不是要求规划阶段先运行尚未实现的测试。
3. workflow-engine 的审查恢复准入仅检查 issue.targetTaskIds / closeWhen.taskId 是否在 boundary.taskIds 内，没有结构化验证项影响检查。任务都在边界内，于是 Runtime 消耗 1 次额度并自动重新派发。
4. Planner 尝试修正这两个真实验证命令，被提交边界校验正确拒绝。它随后保留旧验证命令，只在任务完成要求中补 wrapper 文案，提交通过。
5. 第二次独立审查再次准确指出同一命令问题。Runner 仍自动消耗额度并重新派发，恢复额度由本轮开始的 3 次降到 0 次，其中主线程发起的正式 replan 使用 1 次，Runner 自动恢复使用 2 次。

这不是摘要校验的回归，也不是审查无理由找问题。框架允许进入了一个缺乏足够修改权限的自动修复分支；Planner 用文字变化通过结构校验，但未改变解决问题所需的命令，审查再次拒绝。

## 控制缺口

主线程收到的“本轮最多恢复一次”是对话指令，未传入 Runner 的控制状态，不能约束引擎独立触发的自动恢复。因此，不能再把给主线程的一句话描述为已经限制了整条恢复链。本轮未通过修改 policy、清零计数或扩大权限掩盖这一事实。

另外，workflow_retry_action 对已经绑定新 Registry 的失败 planning action，仍先按旧活动 plan 校验 Registry，因此第一次恢复入口被拒；这一调用未消耗额度。随后经代码核对改用正式 replan 受理。

## 应修复的完整边界

- 审查报告把需要修改的 task 和 verification 身份都结构化表达，并校验引用存在。不能依赖从自然语言中提取验证 ID。
- 自动恢复准入在扣额度和派发之前，统一核对完整影响集与 revisionBoundary；缺少任意验证项权限就返回主线程作局部边界决策。
- 主线程本轮恢复上限如果是用户约束，必须通过正式工具参数进入持久化控制合同；Runner 自动恢复与手动恢复共同遵守，重启不能重置该限制。
- 进度判断应检查未解决义务所绑定的真实验证命令/执行合同是否变化；仅补 done 文案不能被当作该命令缺口有进展的证据。
- 本业务的合法修正是让两个下游 producer 的验证命令及公共 runner 的相关 dispatch 经过同一 wrapper，需要明确纳入这两个 verification ID 的局部边界。不能直接整图重写，也不能通过重置预算使它重新开始。

验收至少覆盖：任务在边界内但验证项在边界外时零派发/零扣额度；明确批准两个验证项后局部修正；未受影响定义和候选保持；仅文案变化不关闭命令义务；每轮手动与自动恢复共同受限；重启保留额度和约束。当前记录只是缺陷复现和修复要求，不是这些修改已完成的声明。
