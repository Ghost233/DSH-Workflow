# 下一轮候选Review接线边界

R59产生pendingPlanRevision，现有workflow-state在pending候选分支会安排plan-revision-review，再由driveWorkflow调用reviewPendingPlanRevision。后者仍是旧长持workflow锁入口，直接requestValidatedPlanReview的最多两次runChild未接新账本。当前不是完整T15端到端完成，下一轮必须优先消费新候选固定的recoveryOrigin/recoveryRequestId。

Review需要在相同规划入口资源租约下固定candidate planDigest/parent/原始Planner receipt、Review prompt及每次独立operation intent，离开workflow内存锁后调用R58适配器。source execution version保持active A，candidate C另作被审查内容绑定。成功结构提交后仍需复用requestValidatedPlanReview里的taskId、abstract、needs_split/decision/discovery及重复问题语义门禁，再在最新状态原子保存Review、convergence与预算结果。

requestValidatedPlanReview目前catch包住runChild及语义校验，可产生第二次调用；新接线不可一次领取包住该循环。候选通过语义审查是Review operation成功，不等于原问题关闭；needs_revision等有效Review结果也需要明确定义与后续候选重建的独立operation身份，不能因Review内容不passed就伪造成传输失败重复问同一Reviewer。

候选被废弃时必须保留原root及Planner/Review回执，用新候选步骤关联同一来源。不能让R59 candidate_staged旧记录缺pending候选后被当作免费重建许可。版本批准/激活与T18预算继承同步推进；当前旧审批路径未获得新协议全量验收依据。
