## 已准备的核心场景

`--entry-runtime` 复用既有 Web stage 和官方 packaged Host 的 headless 场景，使用自动选择的隔离端口 0、独立 profile、private SDK socket；不打开本机官方 Desktop GUI，不操作用户 33080。既有管理 UI 仅完成密码输入与 Web 启动。进入 T06 callback 后，窗口/入口观测全部用 `ctx.state()`，窗口激活只由正式 SDK `openWindow` 发起；不调用会自动发送 ownEntry 的 `ctx.ui()`。

核心场景按同一真实资源顺序验证：首次接管成功时菜单已经隐藏；隐藏菜单时关闭管理窗口后业务继续，SDK 再次打开并激活实际窗口；显式归还入口；再次接管后关闭 official manager listener 并核对入口恢复；重连后再次打开窗口；再接管后只关闭 accepted official SDK session，核对入口恢复和业务连续；再次重连、接管、关窗、SDK 激活与归还；最后独立发出 Web recycle 并检查 Host 继续与实际私有访问端口可重绑定。

每个检查点设计保存 native snapshot、Flutter errors、official Web status（连接时）、同一个 supervisor/Host/launcher PID 的 `kill -0`、实际 receipt 的 PID/lease、认证 Web Owner health 与 direct Host health。断线时不伪造 SDK status，保存 `webStatus=null`，以实际进程、lease 和认证访问核对连续；重连后重新从正式 SDK 核对同一 Web instance。接管原始 reply 和**应答后的立即原生状态**写入 `entry-sdk-requests.jsonl`，不以“稍后隐藏”替代成功应答承诺。截图只在 SDK 已激活窗口时取得。
