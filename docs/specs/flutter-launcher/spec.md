## 问题陈述

工具维护者同时维护 MacLauncher 管理端和 DSH 启动器，原有启动器使用不同的界面与工程技术，需要分别维护窗口、入口、服务控制、构建和分发。使用者希望在统一入口管理自己的工具，同时仍能独立启动 DSH，继续使用既有配置、会话、插件和 Desktop 后端。

此前迁移先实施、后补规格，只有范围决策和构建结果，缺少正式 Spec、Ticket 以及用户故事与验收证据的对应关系。需要将已讨论的需求形成可追踪的规格，供后续拆票和逐项验收使用。

## 解决方案

将 DSH 启动器的管理界面和应用侧控制迁移到 Flutter，直接接入官方 MacLauncher Dart SDK。工具维护者采用同一 Flutter、SDK 和工程规范体系，DSH-Workflow 与 MacLauncher 继续独立维护、构建和分发。

MacLauncher 管理端可以管理 Web 访问服务、观察 Desktop 后端、打开管理窗口并协作入口接管。DSH 启动器拥有自己的业务生命周期；独立运行、管理端断线以及入口归还均保持可用。Owner 工作流和 DSH 业务代码继续使用既有实现。

## 实现决策

1. 本次统一启动器层，保留 Owner 工作流、DSH 业务实现及第三方维护边界。DSH-Workflow 和 MacLauncher 采用同技术体系、独立仓库的维护方式。
2. Flutter 承担管理界面与应用侧业务控制；macOS 原生接口承担窗口、菜单入口、登录项、应用打开和既有配置兼容。应用生命周期与业务控制模块提供统一入口，界面和 SDK 使用相同的业务动作与权威状态。
3. 直接依赖官方纯 Dart SDK，不另建 Swift SDK 代理进程，也不在 DSH 启动器中创建第二个 MacLauncher 管理端。SDK 依赖固定到实际可解析的 Git 提交，并记录真实生成的依赖锁定结果。
4. 项目身份为 dsh-workflow。Web 访问服务身份为 web，声明启动、服务回收、状态和日志；Desktop 后端身份为 desktop，仅声明状态。能力声明与实际回调保持一致，未声明的控制动作返回不支持。
5. 应用使用官方 SDK 的用户级连接约定，并通过关联信息声明项目、服务与应用入口。已打包应用的关联信息应随应用一起移动并正确指向该应用。
6. DSH 启动器拥有 Web 访问资源，官方桌面端拥有 Desktop 后端。Web 启动连接该后端，沿用稳定的访问端口 33080 和既有认证入口；需要时打开官方桌面端，而非再创建一个 DSH 业务实例。
7. Web 服务回收释放启动器拥有的监督进程与访问资源。Web 重连可以恢复仍存活的监督进程的连接，并产生对应新连接的真实运行实例身份。Desktop 后端不随 Web 服务回收或管理端断线而终止。
8. 界面和 SDK 的 Web 启动、回收和重连遵守同一互斥边界。启动进程尚未返回、管理端重新连接及旧请求仍在执行时，冲突操作仍须得到准确结果。
9. 状态依据业务观测生成。真实 Web 运行身份独立于 SDK 会话和进程编号；Desktop 后端使用可信后端运行记录及就绪检查。已确认进程存活但健康查询不可用时，保留运行事实并表达就绪信息不足。
10. 日志保留原始文本。来源未提供的写入时间和流类型保持未知；批次的观测时间不替代日志写入时间。日志实例范围与实际运行对应，重连和重启不混入前一实例内容，截断判断反映实际丢失或限量读取。
11. 入口接管成功以原生菜单的实际隐藏结果为准。管理端失联、接管失败和断线后迟到的接管动作均须归还入口；入口动作与业务服务回收分开处理。打开管理窗口应能激活真实原生窗口。
12. 重复退出等待同一清理过程。启动未完成或子进程暂停、无法正常响应退出时，仍须结算启动器拥有的执行范围再退出；保持 Desktop 后端的独立生命周期。
13. 兼容既有应用身份、数据位置、偏好键、内网密码存储和旧钥匙串只读迁移。内网密码仅用于应用自己的访问认证，不通过 SDK 声明、状态或日志接口传递。
14. 保留完整访问权限、局域网设置、密码、登录项、稳定版更新和插件管理。设置与插件变更按各自生命周期生效，界面明确需要重连 Web 或完全重新打开 Desktop 后端的情况；不得通过自动关闭用户后端替代提示。
15. 当前工程基线为 Flutter 3.47.6、Dart 3.13.5，macOS 最低版本保留为 14。依赖解析、格式、静态分析、测试与构建使用统一工程约定；静态分析通过的标准为零诊断。
16. 独立应用包含 Flutter Release、独立 Node 运行时、官方 Desktop 和项目集成资源。分发产物不依赖开发者的源码 checkout 或系统安装的业务依赖。构建与独立运行验收在两个架构上分别执行，签名和 DMG 校验保持实际检查。
17. main 构建产物与正式发行保持不同的发布语义。稳定版更新继续按本项目的 macos-v 发行版本选择；本次规格不授予安装替换当前运行应用或发布新 Release 的权限。

## 测试决策

1. 用户已确认以打包后的 DSH 启动器应用边界为主要验收接缝：通过正式 MacLauncher SDK 验证服务与入口协作，通过管理窗口验证设置、更新和插件管理，再用真实原生窗口及双架构 DMG 验收补充分发证据。优先复用该边界，不为每个实现模块另建测试入口。
2. 好的测试验证外部可见结果：资源是否实际启动或释放、后端是否继续运行、窗口和入口是否确实可见、状态与日志是否对应真实实例、配置是否保留、应用是否可以离开源码目录运行。私有字段、方法调用次数和测试替身的成功不单独构成交付证明。
3. SDK 验收覆盖能力声明、正式连接、启动与服务回收、状态和日志、打开窗口、入口接管、断线与重新连接。不支持的 Desktop 控制必须明确失败；管理端断线必须归还入口并保持业务运行。
4. 业务生命周期验收覆盖已有后端连接、缺少后端时的打开与就绪等待、Desktop 退出和实例变化后的重连、重复启动、界面与 SDK 并发控制、启动尚未完成时的回收冲突，以及新连接不重复占用访问端口。
5. 退出验收覆盖 DSH 启动器正常退出、重复退出、启动尚未完成时退出，以及暂停或不响应正常终止的自有受控子进程；核对启动器拥有的 Web、SDK 连接及客户端等资源释放。独立 Desktop 后端可以继续运行，其退出、存活或收据不作为启动器退出失败的条件。
6. 状态与日志验收验证真实运行身份、就绪信息及观测时间；后端健康查询失败不得抹去已经观测到的进程存活事实。验证日志原始文本、未知时间和流类型、跨实例隔离，以及恰好等于读取上限时不误报截断。
7. 管理窗口验收覆盖三个页面、受支持的最小窗口尺寸、操作失败可见性、关闭窗口后业务继续运行、重复打开激活现有实例，以及管理端入口接管后仍可打开窗口。
8. 兼容与设置验收覆盖迁移前配置和密码、权限与局域网设置的生效规则、系统登录项批准状态、稳定版更新筛选、插件版本与兼容信息、更新结果和重新加载提示。对输入失败和真实依赖失败记录实际结果。 完整访问权限仅验证设置保存、实际持久化、错误可见性与需要重开的提示；不强制重开独立 Desktop 或验证新 Desktop 实际采用权限。
9. 分发验收在 arm64 和 x64 分别检查 Release 应用、签名与 DMG；移动应用到独立临时位置，验证真实 Host、前端、DOCX/XLSX/PPTX 转换、Owner 就绪与 Matt 面板装配。只运行 Flutter 编译或存在产物文件不足以证明独立运行。
10. 可复用的现有证据来源包括官方 SDK 的真实 Unix socket 集成测试、真实 Node 进程控制测试、Web 连接与 Desktop 后端观测测试、管理窗口布局测试、真实原生窗口探针、更新选择测试和移动应用后的运行时验收。替身测试说明其覆盖范围，真实应用与 SDK 的完整调用链另行核对。
11. 测试采用隔离数据、临时 profile 和受控资源，保持用户当前配置和运行服务。第三方错误按维护边界如实报告；工程环境缺失记录验证失败，由工程初始化流程处理。
12. 后续 Ticket 必须将用户故事映射到验收场景、固定验证命令和执行证据，并标明待验收、通过、失败或未执行。已有 CI 结果只能用于它实际覆盖的场景，不能据此将全部用户故事自动标为通过。
