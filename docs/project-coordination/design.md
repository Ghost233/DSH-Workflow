# 独立插件方案

用户于 2026-11-10 通过 Q15 确认本方案，设计定稿。本次确认不启动实现、安装、权限配置或隔离原型。

## 结论与证据范围

Tobs v1.6.1 和配套 DSH 0.2.1-rc.3 已提供本方案所需的主要服务接缝。可以组合实现 GitHub 触发、多层分工和逐级汇报，无需引入 SuperAgent 或修改上游源码。

这个结论来自源码、实际 npm 发布物和类型契约核验。组合行为仍需隔离原型验证，当前不能视为运行验收通过。详细证据见[接口核验](interface-audit.md)。

普通 Bot 的公开接口不能精确绑定当前 Turn 的来源。用户已在 Q14 接受 Host 可核验消息、原文绑定和短期单次接单凭证方案，不把精确 Turn 绑定列为首版要求。

本稿覆盖首版单机、同一个 DSH Host 内的独立插件。它管理多个仓库和多层 Bot。已有第三方插件、当前项目及用户正在运行的服务均不在本轮修改范围内。

## 组成与边界

| 部分 | 责任 |
| --- | --- |
| Tobs | Bot 身份、记忆、模型计划、收件箱、原生执行会话、原生报告和工作区 Grant |
| DSH | 模型调用、Agent 工具域、Workspace Registry 和运行时能力 |
| 独立插件 | GitHub 轮询、准入、任务树、依赖、派工记录、结构化报告、验收与恢复 |
| GitHub | 正式开发 Issue、代码提交、PR、评审、CI 和合并事实 |
| 工程初始化流程 | 工具链、依赖、缓存和项目验证环境的准备 |

插件使用自己的持久存储，首版采用本地 SQLite。它不写 Tobs 内部数据表，不导入未公开源码路径。Tobs 服务通过 botharness 注入，类型引用实际发布的 @botharness/core 根包。

插件只处理自己关联的任务和执行，不接管成员在其他聊天中的无关工作。

## 组织和任务

长期成员均为独立 Tobs Bot。总负责人协调跨仓库目标；仓库负责人承担本仓库需求；专业负责人和执行者可以继续形成下级。层级不固定为三层，插件校验父子关系无环，并受部署时的深度、成员数和并发上限约束。

组织关系与任务关系分别记录。一位成员可以承担多项任务；每项任务只有一位当前负责人。上级发出派工后，在接收方明确接受前仍承担分派责任。拒绝、澄清和验收均回到直接上级。

开发执行任务限定一个主仓库。跨仓库需求拆成各仓库的任务，由内部总需求关联。需要独立验收的开发任务对应 GitHub Issue；临时调查不强制建 Issue。

任务父子关系表示责任树。任务依赖单独记录，必须无环；依赖可以要求成果已交付或最终完成，不能用组织层级代替。拆分方案由负责人提出，插件校验范围、关系和授权后保存。

## 最小持久记录

| 记录 | 必须保留的业务事实 |
| --- | --- |
| 成员绑定 | Bot 身份、插件角色、主仓库、上级、模板和授权范围、收尾或暂停状态 |
| 项目事件 | 原始对象身份、仓库、来源账号、观察版本、内容引用、准入决定和消费状态 |
| 任务 | 稳定任务 ID、父任务、负责人、范围、验收条件、授权依据、Issue、交付状态和人工停止记录 |
| 任务依赖 | 前后任务、依赖要求的交付阶段、变更者和版本 |
| 执行尝试 | 派工 ID、任务、Bot、原生 Session、Grant、Workspace、工作目录和执行观察结果 |
| 动作记录 | 创建 Issue、派工、创建 PR、报告等动作的操作键、请求摘要、已确认或结果未知状态 |
| 报告和验收 | 真实提交者、任务与执行绑定、结构化状态、证据、上级验收和上报记录 |

不复制全部聊天或模型推理记录。长期偏好与项目经验留在 Bot 记忆；当前任务状态和授权以这些业务记录为依据。

## GitHub 接入

首版每 60 秒轮询配置的仓库，采用分页、增量位置、重叠读取和对象版本去重。初次启用读取未关闭的 Issue 与已关联任务；历史关闭任务按明确回补范围读取，不静默重跑全部历史。

Issue 列表也会返回 PR，插件按对象类型区分。Issue/PR 普通评论、PR 代码评审、评审决定和 CI 结果分别读取；对活跃任务关联的 PR 做重点检查。不能只读取 Issue 列表就宣称覆盖了评审和 CI。

轮询位置只在对应结果持久化后推进。断网、限流和服务异常保留位置；恢复后重叠读取。遵守 Retry-After、限流重置时间和条件请求，不用高频请求代替恢复机制。

轮询只能补拉仍可查询的变更，不能完整还原轮询间隔内创建后删除的内容或所有中间状态。对象作者也不等于每次编辑的操作者。无法核验编辑者的变更只作为上下文；扩大授权需要有可核验来源的新指令。

依据：[Issue API](https://docs.github.com/en/rest/issues/issues#list-repository-issues)、[仓库评论 API](https://docs.github.com/en/rest/issues/comments#list-issue-comments-for-a-repository)、[API 调用建议](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)。

## 准入和授权

用户与白名单 GitHub 成员可以在已授权范围内发起开发。其他来源可进入分析、分类和上报，不因此获得提交代码的授权。插件自己创建的子 Issue 依据已记录的父任务授权继续，不依赖 GitHub 账号名称猜测来源。

每次拆分和派工都核对仓库、工作范围、调用者、父任务和当前停止状态。子任务不能扩大父任务授权，成员描述中的角色标签和模板正文不能授予权限。

聊天总需求必须基于 Host 可核验的 Human DM Admission 和原始消息。插件为近期未受理来源签发一次性凭证，绑定实际 Bot、原文版本、时效和授权；同一来源重复受理返回同一任务。模型自报的 source_ref、记忆中的旧指令或历史上下文均不能单独创建新授权。

职责内可以自动澄清、拆分、建 Issue、派工、提交代码及创建或更新 PR。合并、正式发布和扩大权限需要用户明确授权。

插件可以约束自己的工具和动作，不能据此声称限制了所有原生 Shell 或所有第三方工具。部署时仍须使用适当的 GitHub 身份、仓库规则和原生权限配置，落实合并与发布边界。

## 事件如何唤醒 Bot

1. 插件校验并持久保存事件及来源。
2. 插件确认成员未暂停、插件接入已启用，然后安排系统唤醒。
3. 目标 Bot 的专用 Schedule 调用 runNow，产生 system 事件。
4. Bot 通过插件的 Agent-local 工具领取待处理事件。
5. Bot 提出接单、拒绝、澄清或拆分决定，插件校验并保存。
6. 保存决定和必要后续动作后，插件确认事件已处理。

专用 Schedule 关闭周期执行并锁定配置，只作为唤醒信号。它不存储 GitHub 事件，也不表示外部发起者获得 Human 权限。插件有独立启停开关。

唤醒可合并。待办领取使用租约和确认，剩余分页、过期租约、重启和失败信号由插件重新检查。处理语义为至少一次，业务动作使用稳定操作键和对账，不能承诺所有外部副作用恰好一次。

## 结构化工具与调用身份

以下是插件计划提供的工具职责，具体接口名称在实现时确定：

| 工具职责 | 可调用角色 | 插件负责校验 |
| --- | --- | --- |
| 领取待办、查询任务 | 已绑定成员 | 自己的任务和获准查看的下级范围 |
| 接受、拒绝、请求澄清 | 被派工的成员 | 派工对象、版本和上级 |
| 提交拆分、请求成员 | 当前负责人 | 子范围、岗位模板、依赖和容量 |
| 预留执行、绑定原生执行 | 任务负责人及对应执行者 | Bot、真实 Session、Grant、Workspace 和派工记录 |
| 提交进度、证据和成果 | 对应执行者 | 原生归属、任务绑定、代码版本与证据 |
| 验收、退回、向上汇报 | 直接上级 | 子任务关系和验收条件 |
| 停止、恢复 | 用户或有权限的负责人 | 停止来源、子树范围和恢复权 |

工具在 Agent setup 时注册。身份来自实际 Agent、Tobs 提供的 botSlug/rootRole 以及持久 ownership，不相信模型参数中自报的 Bot 或 Session 身份。

## 原生执行与派工对账

稳定版由成员自己的 Orchestrator 调用原生 create_assignment，插件不使用主干才放开的外部直派能力。

一个原生 Assignment 同时只绑定一项插件任务。同一任务可以经历多次执行尝试，不能让两个独立开发任务共享同一个执行会话。

1. 插件先保存派工 ID、任务范围、目标 Bot、工作目录和授权记录。
2. 负责人取得派工信息，经原生工具创建执行。Continuity Key 可辅助定位该派工。
3. 模型返回的 Session ID 只作为查询提示。插件核对真实 Bot 归属、Grant、Workspace、Key、来源及创建时间后，保存绑定。
4. 执行者通过插件工具取得正式任务和提交业务报告。原生 report_to_orchestrator 继续向所属负责人报告运行情况。
5. 丢失回执或重启时先查询真实执行，再决定继续。无法唯一定位时进入待核实状态，不按标题相似度认领，也不盲目再次 create。

稳定版恢复会清除原生 Continuity Key，因此插件必须保存 Session 绑定。原生记录没有插件业务 taskId 或完整首次 instructions，不能只凭一个真实 Session 就证明任务内容与验收均正确。

## 工作目录和成员权限

并行开发任务使用独立 worktree。插件核验仓库和最终真实路径处于预授权范围，再注册已有目录为 DSH Workspace，为指定 Bot 创建 Grant。

原生 Grant 不会沿成员上下级自动继承。插件每次绑定和恢复都复核路径与仓库归属。更换目录需要新 Workspace 和 Grant；撤销 Grant 后仍要单独确认相关执行已停止。

工程初始化沿用项目已有流程。插件不猜语言或包管理器，不自行安装依赖、创建依赖缓存或改写项目配置。环境缺失时记录真实失败并等待工程准备，不把它当作模型或网络故障无限重跑。

有未提交修改、未跟踪文件或未确认成果时，不自动删除工作目录。提交、推送、合并后的本地同步与清理遵守目标仓库自己的代理约束。

## 自动组队和收尾

负责人可以在预授权模板、模型和容量上限内请求临时专业成员。插件通过带 operationKey 的 Bot 创建服务处理，保存创建回执，防止同一次组队请求生成多个成员。

新成员获得自己的身份和记忆。模型计划和工作区权限分别配置，不复制上级的私密凭据或整个授权范围。插件角色与 Tobs 描述标签分开管理。

缩编时先将成员标为收尾，拒绝新派工，完成或交接已有任务。确认没有活跃执行后再暂停身份，保留记忆和历史。原生 pause 本身不保证已经停止运行。

改变组织关系不自动转移已有任务责任，任务交接需要明确记录。

## 报告、验收和完成

原生报告只回所属 Bot。多层报告通过插件保存业务报告，再唤醒直接上级。普通进展合并；阻塞、需要决定、PR 可审查和最终完成立即上报。每次上报有稳定报告身份和出站记录，重复信号不会重复生成同一条总结。

验收证据包含适用的 Issue/PR、commit 或 head SHA、验证命令及真实退出结果。代码版本变化后，旧验证不能继续作为新版本的通过证据。PR 草稿、检查失败或结果缺失不算已交付。

有代码变更时，成果可审查记为已交付；相关 PR 已合并且验收满足后记为最终完成。父任务还要满足子任务及集成验收要求。GitHub 上单独关闭 Issue 不自动证明任务已完成。

重复问题、已有实现覆盖、无法复现或调查后确认无需修改时，执行者提交证据，由直接上级验收后按无需变更结项。结果中保留原因和证据，不制造无意义的 PR。

用户向总负责人查询时，报告展示各仓库已交付、已合并、等待、阻塞、停止和待决策事项。总负责人可以读取必要下级证据，不依赖各 Bot 的自由文本记忆猜测进度。

## 一个跨仓库场景

用户在总负责人聊天中提出登录需求，涉及前端仓库 A 和后端仓库 B。

1. 总负责人领取真实聊天来源，插件核验单次凭证后建立总需求。
2. 总负责人分别派给 A、B 仓库负责人；两位负责人接受，或把缺失信息退回上级。
3. 两位负责人把可独立验收的工作整理为各自仓库的 Issue，并记录接口契约等依赖。
4. 仓库负责人可以继续分给专业负责人，专业负责人再派给执行 Bot。正式子任务保留父任务、负责人和验收条件。
5. 插件在预授权范围内准备独立 worktree 和 Grant。每位执行 Bot 的 Orchestrator 使用原生 Assignment 实现和验证。
6. 后端成果可审查时，负责人验收证据并标记已交付。满足依赖要求的前端工作继续推进；模型服务不可用的执行等待恢复，其他任务可以继续。
7. 两边成果通过验收后，总负责人向用户报告 PR、验证证据和待审事项。插件不会自行合并或发布。
8. 用户决定合并后，插件读取合并事实，并由上级完成集成验收。满足条件后总需求最终完成；未满足则继续保留具体责任和待办。

用户直接在仓库 A 创建 Issue 时，入口改为 GitHub 轮询。后续接单、派工、验收和汇报共用同一套记录。

## 故障、停止和恢复

网络或模型暂时不可用时保留任务，进入等待恢复，按依赖进行退避探测。依赖恢复后对账再继续，不因固定尝试次数耗尽就把开发任务判为失败。不会持续重建 Bot、重建任务或重发全部指令来探测服务。

恢复沿用已记录的模型计划，不通过自动更换未经批准的模型或服务商规避故障。

认证失效、权限撤销、模型不兼容配置和工程环境缺失分别上报相应处理需求，不伪装成短暂网络故障。实现或测试失败回到当前任务修复，达到部署策略中的时间或预算边界后向上级报告。

每次有外部副作用的动作都先记录意图，再发起，最后记录回执。网络中断后结果不明，先查询 Issue、PR、提交和原生执行。能唯一核对就恢复，无法核对就保留待核实状态。

停止某任务先持久保存控制决定，冻结该任务子树的新派工、重试和唤醒，再停止已绑定执行。只影响该子树，不停止同一 Bot 的其他任务。停止返回不等于全部进程已退出，清理需等待实际确认。

用户停止只能由用户明确恢复；负责人停止可由本人或有权限的上级恢复。主机重启、网络恢复和模型恢复均不能解除人工停止。

## 部署和生命周期

首轮验证固定 Tobs 1.6.1、配套 DSH 0.2.1-rc.3 和插件版本。未来升级先验证服务契约与任务恢复，主干能力不自动计入已发布版本。

插件先加载、注册 setup hook，再建立相关 Agent。安装到已有运行环境时等待合适窗口，不为加载工具静默归档或替换正在工作的会话。停用时先关闭接入与新派工，再撤销工具注册和 hook；工具调用仍检查插件有效状态。

实际仓库、GitHub 凭据引用、成员、执行根目录、模板、模型计划、容量与预算上限由部署配置明确给出。GitHub 身份可以使用部署者选择的专用账号或 App；当前不创建或切换身份，也不修改现有配置。

## 后续验证顺序

1. 服务契约验证：注入 core、注册工具、验证真实调用者，完成专用 Schedule 唤醒。
2. 单仓事件验证：重复轮询只产生一个业务处理结果，来源准入正确，暂停和重启不丢待办。
3. 单任务开发验证：原生派工、Session 对账、独立目录、结构化证据和 PR 交付。
4. 多层协作验证：总负责人、仓库负责人、专业负责人和执行者之间接受、拒绝、拆分、验收和上报。
5. 故障验证：回执丢失、断网、模型不可用、Host 重启、人工停止及恢复，不重复外部副作用。
6. 动态成员验证：创建请求重试、收尾归档、权限范围、已有会话接入和插件停用。

每项验证都记录源码与包版本、命令、实际结果和缺口。本轮只形成这些验收要求，不编写或运行原型。
